# Shell trust and the capability-policy layer

Compacted on 2026-10-17 from 14 August 2026 reasoning traces. Bodies live in
git history; every decision, rejection, trap and verbatim owner ruling the
sources carried is reproduced below.

## What this theme settled

`GA-37`/`D28` pinned five concrete shell-trust guarantees as `AT-LF-20` through
`AT-LF-24`: one execution per exact plan digest; filesystem and environment
isolation with an explicit env allowlist and no blanket inheritance;
default-deny outbound network; resource and time caps reported as their own
distinct non-passing states; and refusal of any repository-supplied symlink
whose real target resolves outside the repository. The owner chose to freeze
the oracle first with the target behaviour pinned, sign it, then implement
against the frozen shell — so a red gate between drafting and implementation
is the tests doing their job.

The work then produced the project's most expensive named anti-pattern:
**guarantee sharding**. A single cross-cutting guarantee was split into
independently-branched, independently-tested tickets, and each ticket's test
proved only its own named slice, not the guarantee — so every branch could be
green while the guarantee was still false. It was filed as its own wiki
directory, `mistakes/guarantee-sharding.md`, at the user's explicit request.
The fix landed as one pass on one branch (RIG-138/139/140) rather than merging
any of the five sibling `rig-115-at-lf-*` branches.

`RIG-137` removed a production `net.Server.prototype.listen` monkey-patch that
globally weakened network isolation to work around a frozen test's timing. The
owner chose Option A — unfreeze and correctly fix `AT-LF-22`'s timing, delete
the production patch — and explicitly rejected a smaller sibling-workspace fix
that dropped the loopback host, because `listen()`'s async behaviour and the
`'listening'` event are Node's documented contract while a synchronous
`address()` after a bare `listen(0)` is incidental runtime behaviour.

The structurally worst finding came from a fresh independent review: an entire,
real, well-tested safety layer sat on a code path the installed product never
takes. The existing guard against that class of bug — "the oracle is green at a
seam the product does not use" — operated at file granularity, so it passed
while the four functions carrying the guarantees were never called. One layer
deeper, the runner CI actually executes turned out to be a separate
hand-maintained duplicate.

`RIG-144`/`GA-38`/`AD-39` then built the capability-policy layer on the
shipping runner, with three owner corrections: undeclared network is a
**temporary compatibility state**, not silent allow; the second runner is
**eliminated**, not drift-tested; and CI authority is **committed policy or
refuse** — no ephemeral env var, no implicit yes, no prompting. Resource limits
are configurable defaults, not hard limits, with the invariant
`0 < t_command <= t_authorised` and `0 < M_command <= M_authorised`.

### 2026-08-26-rig115-shell-trust-guarantees.md
- **Summary:** GA-37/D28 — the owner approves five concrete shell-trust defaults as AT-LF-20..24, to be frozen before implementation.
- **Decisions:** GA-37, D28
- **Status:** historical
- **What it recorded:** That the existing signed oracle disclosed the untrusted-task boundary via `AT-LF-5` carrying `GA-26`'s five words, but never pinned down what any of them concretely guarantee — session lifetime, filesystem/environment isolation, memory limits and symlink handling were labeled assumptions, and network denial was requested but unenforced. The agent proposed five defaults as the smallest reasonable reading of `GA-26` that is also deterministically testable; the owner approved all five as stated.
- **Verbatim rulings / rejections / traps:** The five, verbatim: "1. **Approval lifetime.** A plan approval authorizes exactly one execution of that exact plan digest. It does not carry over to a later run — re-using a consumed approval is not authorization. 2. **Filesystem/environment isolation.** A task's working directory, and every path it touches, must resolve inside the repository even through a symlink. It receives no ambient environment variables beyond an explicit allowlist — no blanket inheritance of the parent process's environment. 3. **Network denial.** A task has no outbound network reachability by default. Nothing is reachable unless the plan explicitly allows it. 4. **Resource/time caps.** A task that exceeds a configured memory ceiling or wall-clock timeout is killed and reported as its own distinct non-passing state, per the abnormal-ending taxonomy already frozen (`GA-33`) rather than hanging or being silently truncated. 5. **Symlink handling.** A repository-supplied symlink whose real target resolves outside the repository is refused the same as any other escape attempt — Rig never follows it to read, write, or set a working directory." Authority note: "None of that is an implementing agent's call to make — it is a product-safety promise, not a mechanism detail." Order chosen: "freeze the oracle first with the target behaviour pinned down, sign it, then implement against the frozen shell. A red gate on these five cases between drafting and implementation is not a regression; it is the tests doing their job."

### 2026-08-28-linux-network-isolation-ci.md
- **Summary:** Linux CI failures had one shared cause — command availability was checked instead of capability availability; the fix probes the exact rootless unshare prefix.
- **Decisions:** none
- **Status:** historical
- **What it recorded:** The implementation checked that `unshare` existed by running `unshare --help`, then assumed `unshare --net -- <task>` would execute; on an unprivileged Ubuntu runner, creating a network namespace without entering a user namespace fails before the task starts — making a mutating task appear clean, a timed-out task appear clean, and the network-denial test pass vacuously. ### 2026-08-29-rig144-execution-policy-design.md
- **Summary:** AD-39/GA-38 — a separate, target-owned .rig/execution-policy.json is the smallest safe authority; service bindings cannot supply their own authority.
- **Decisions:** AD-39, GA-38
- **Status:** historical
- **What it recorded:** Why extending `.rig/service-bindings.json` loses: it is Rig-owned output, so a changed binding could request and supply its own authority in the same generated file. The v1 schema in full, keyed by the existing service ID. The grant rules: a command may request a smaller-than-default ceiling without a grant; a request above the 10-minute / 2 GiB defaults must be no greater than the committed grant; `network: "required"` needs the exact network grant while `network: "none"` is a restriction needing none; omitted network runs only as a distinct `undeclared` compatibility state with a diagnostic. Where the shared evaluator belongs and why. The implementation slices.
- **Verbatim rulings / rejections / traps:** Authority condition: "it is seeded on install, retained as user bytes, and only grants take effect when the exact file is tracked and clean in Git." Forward-compatibility: "This makes a future default-deny flip a policy change, not a schema migration." Evaluator shape: "It returns either an executable normalized capability record or a named refusal, so a future interactive one-use grant can call the same evaluator with an additional authority source rather than reimplementing CI policy.
