# Turn 4 — what "a human must sign" can actually be checked

Follows `2026-09-02-gate1-multi-principal-forgery.md`. The owner clarified that
"any key not generated by the agent" meant something specific:

> We would only allow keys where the user has to give their password to sign off
> on the gate and any human needs to sign things. Like the FIDO key for mac or
> the ssh key on my ubuntu. I had to create it manually.

That is a **human-presence** requirement, not a key-identity one. It is a better
articulation of the goal than either previous turn. It is also only half
checkable, and the half that works lives in the file the owner asked to delete.

## Finding 1 — a passphrase is cryptographically invisible (tested)

Signed the same message with the same key, before and after protecting the
private key with `ssh-keygen -p -N 'hunter2'`:

```
cmp nopass.sig withpass.sig  →  IDENTICAL BYTES
```

Ed25519 is deterministic, so the two signatures are not merely both valid, they
are **byte-identical**. A passphrase protects the key file at rest on the
owner's disk; it leaves no trace whatsoever in the artifact. Worse, once the key
is loaded into `ssh-agent` the passphrase is not requested again, so even the
owner's own experience of "I typed my password" does not correspond to any
per-signature event.

**Therefore:** "the Ubuntu key I created manually and protected with a password"
cannot be distinguished, by any verifier, from a key the agent generated one
second earlier with `ssh-keygen -t ed25519 -N ''`. This is recorded as a rejected
approach: *"a passphrase-protected key proves a human signed."* It proves
nothing that is machine-checkable.

## Finding 2 — FIDO presence *is* enforceable, from the signers file (tested)

OpenSSH 9.6 supports the `verify-required` option on an allowed-signers
principal line. Against a plain `ssh-ed25519` key it fails closed:

```
gate1-owner namespaces="rig-gate1" verify-required ssh-ed25519 AAAA...
→ allowed:1: invalid key / Could not verify signature. (exit 255)
```

`verify-required` is meaningful only for the FIDO algorithms `ecdsa-sk` and
`ed25519-sk`, and it demands that the signature record that the user was
**verified** (PIN), not merely present. That is exactly the property the owner
wants — and it is expressed as *data in `gate1.allowed-signers`*, needing no code
change and no unfreeze, because that file is not in the freeze digest.

**The irony worth recording:** the signers file the owner asked to remove is the
only place OpenSSH lets you say "a human must be physically verified to sign."
Deleting the file deletes the mechanism. Keeping it as a one-line generated pin
keeps it.

## Finding 3 — key-type checks alone are still forgeable

Requiring an `sk-` key type *without* pinning the specific key does not hold. The
sk-ed25519 signature is ed25519 over `SHA256(application) || flags || counter ||
SHA256(message)`; an agent that cannot run `ssh-keygen -t ed25519-sk` (no token)
can still implement that construction in software with a self-made key and set
the user-presence flag byte itself. The pin is what makes it unforgeable, because
the agent cannot produce the matching private key. **Pinning survives every
variant of this design.**

## Constraint discovered — the verifier is a frozen file

`scripts/check-advanced-spec.js` is listed in
`wiki/gate1/testing-infrastructure.manifest` (digest `2980d274…`). Any edit to
it changes the manifest digest, changes `oracleMessage`, and breaks the
signature. The single-principal security fix therefore requires the full
unfreeze ceremony: a filled `wiki/gate1/unfreeze-request.template.md`, the owner
editing, and `node scripts/approve-gate1.js --confirm-digest-delta <digest>`.
The `approve-gate1.js` fix and the test-file changes are **not** frozen and cost
nothing.

## Constraint discovered — enforcement must be structural, not name-based

The frozen test `AT-GATE-2` (`tests/advanced-spec-gate.test.js:58-70`) signs with
a principal literally named **`owner`** and asserts
`verified.principal === 'owner'`. So the verifier must enforce *"exactly one
principal"*, **not** *"the principal must be named `gate1-owner`"*. A name-based
rule would break a frozen test and force a second unfreeze for no security gain —
the structural rule already closes the forgery completely, since an appended
`rig-bot` line makes the file invalid regardless of naming.

## Done this turn

- The five-line `# key-class:` block was removed from
  `wiki/gate1/gate1.allowed-signers`; it is now a single generated pin line. The
  oracle still verifies (`principal=gate1-owner fingerprint=SHA256:MYPMlpxH/…`,
  14 files, 83 cases) — confirming the file is outside the freeze digest and this
  needed no re-sign. Provenance remains in `wiki/topics/gate1-signing.md`.
- Tests rewritten in `tests/gate1-approval-script.test.js` (not a frozen file):
  9 tests, 7 green, **2 red by design**.
  - green: *re-signing regenerates the signers file as a single pinned principal
    line* — passes against current code, because the ceremony already writes a
    one-line template. The "generated file" decision needs **no script change**;
    this test locks the behaviour in as a regression guard.
  - red: *a second principal line cannot ratify a forged oracle* — the verifier
    fix (frozen file, needs unfreeze).
  - red: *an unexpected non-owner principal line is not silently dropped* — the
    ceremony guard (not frozen, free).

## Open — owner decision, not blocking the above

Whether to move to a FIDO key and add `verify-required`. Cost: the current
Ubuntu `ssh-ed25519` key stops working the moment that option is added, so it
requires enrolling a hardware token (or macOS Secretive) and re-signing. Benefit:
human presence becomes genuinely enforced rather than assumed. The two red tests
above are worth fixing regardless of how this lands.
