Followed up on the guarantee-sharding diagnosis
([2026-08-27-guarantee-sharding-mistake.md](2026-08-27-guarantee-sharding-mistake.md))
by implementing the fix for RIG-138/139/140 directly on this branch, driven
by the red `tests/guarantee-coverage.test.js` (AT-PROC-1a/b/c) already
written against it, rather than merging any of the five sibling
`rig-115-at-lf-*` branches.

Checked `wiki/gate1/acceptance.md` on this branch first: it is signed through
`AT-LF-19` only (2026-08-21, D21). `AT-LF-20`–`AT-LF-24` exist as frozen text
on `rig-115-at-lf-24-symlink-escape`'s own copy of `acceptance.md` (a
2026-08-26 re-sign, 68→73 cases) but that re-sign never merged to this
lineage, and that text is already correctly scoped to the whole guarantee —
it was the *tests* implementers wrote against it, and the implementations
themselves, that narrowed. So this work did not need a new grilling round or
re-sign; it needed the existing AT-PROC-1 red tests turned green.

## What shipped

1. **AT-LF-20 (durable one-use approval).** `executePlan` now requires
   `plan.target` and calls a new `consumePlanApproval(target, plan)` that
   atomically creates `target/.rig/lint-format/executions/<sha256(plan_digest)>.json`
   with `{flag: 'wx'}` before checking command drift. A second, independently
   constructed approval object for the same `plan_digest` — including from a
   second process — sees the file already exists and gets `not_authorized`,
   not a thrown exception (matching the function's existing status-object
   convention for `command_drift`/`executed`). Consumption happens before the
   drift check: a drifted plan needs a fresh plan (new digest) and thus a
   fresh approval regardless, per `GA-31`/command-drift's existing "a changed
   command is a new command" ruling.

   Note for a later pass: `rig/lib/enforcement.js`'s `consumeOneUseApproval`
   has the identical in-memory-only defect, and
   `wiki/reasoning/2026-08-22-mvp-release-review.md` already flagged it as
   never actually consuming (no caller persists the flag).
   `rig/lib/policy.js`'s `grantApproval` writes a durable approval file
   (`.rig/approvals/<action_digest>.json`) but nothing reads it back and
   marks it used — the write half of a durable one-use approval exists
   generically, the consume half does not, for any caller. Lint-format's fix
   here is local to `lint-format.js` and does not touch `enforcement.js`.

2. **AT-LF-21/24 (symlink/cwd containment).** Added `taskCwd(target, rel)`
   (wraps `containedPath` from `path-safety.js`) and routed both `runGrade`
   (which gained a `target` parameter it did not have before) and
   `runReadOnly` (which previously did a naive `path.join` with no
   containment at all — worse than the sibling branches' asymmetry, since
   here neither call site was guarded) through it. An escape now reports
   `boundary_violation` — per-command in `runGrade`, whole-run in
   `runReadOnly` — instead of throwing uncaught or silently following the
   link.

3. **AT-LF-23 (memory ceiling).** See the enforcement-design note in
   [`mistakes/guarantee-sharding.md`](../mistakes/guarantee-sharding.md) for
   the full argument. Summary: `spawnSync` blocks the event loop, so a memory
   watchdog can't poll RSS from the same process without going async — and
   going async broke four frozen `tests/advanced-oracle.test.js` cases
   (`AT-LF-7/8/9/11`, digest-checked in
   `wiki/gate1/testing-infrastructure.manifest`). Landed a separate-process
   watchdog instead (`rig/lib/memory-guarded-exec.js`): the caller stays a
   plain synchronous `spawnSync` on the watcher, which itself spawns the real
   command asynchronously and polls `ps -o rss=` every 15ms, `SIGKILL`ing on
   breach and reporting through a result file. Enforcement moved to a
   different process rather than a different calling convention.

## Two mistakes caught before landing, not after

- Edited `tests/helpers/advanced.js` (`withTempDir`/`withRepo`) to support
  async callbacks for the first (async) attempt. `npm test`'s Gate 1
  protection (`scripts/check-advanced-spec.js`, principal `gate1-owner`)
  failed immediately: that file is frozen testing infrastructure. Reverted
  and wrote a local `withRepoAsync` in the test file instead — moot once the
  sync/watcher redesign removed the need for it, but the actual data point is
  the gate catching an out-of-authority edit to a signed file before it
  reached CI, exactly as designed.
- The first `AT-PROC-1c` fixture (one instant 200MB `Buffer.alloc`) was
  flaky, ~1-in-8 local runs, because a single fast allocation can complete
  inside one 15ms poll window. Rewrote it to grow in twenty 10MB chunks with
  a short pause between each — closer to how a real runaway process grows,
  and it gives the watchdog several samples before completion. 15 consecutive
  clean runs after the change, 0 before (across ~15 runs, 1 in 8 failed).
