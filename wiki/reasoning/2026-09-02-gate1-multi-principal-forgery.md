# The allowed-signers *list* is the hole, not the comments

Follows `2026-09-02-gate1-allowed-signers-remove-list-pushback.md`. Turn 3 of
the grill. The owner pushed again: *"Why are we maintaining a who-is-allowed-to-sign
register? Any key that cannot be generated and signed by the agent is good
enough. Allowed signers is more of an access-control thing we do not really need."*

Rather than restate turn 2, the claim was tested. The test changes the finding.

## Demonstrated forgery (reproduced, not theorised)

`verifySignature` (`scripts/check-advanced-spec.js:87-101`) reads **all**
principals out of `gate1.allowed-signers` and loops:

```js
const principals = signerPrincipals(allowedText);
for (const principal of principals) {
  const result = spawnSync('ssh-keygen', ['-Y','verify','-f',allowed,'-I',principal, ...]);
  if (result.status === 0) { return { armed: true, principal, fingerprint }; }
}
```

It returns success on the **first principal that verifies** and never asserts
*which* principal that was. Consequence, executed end to end in a temp repo:

1. Owner arms the gate normally → `principal=gate1-owner`.
2. Agent runs `ssh-keygen -t ed25519` and **appends** one line:
   `rig-bot namespaces="rig-gate1" <its own pubkey>`. The `gate1-owner` line is
   left in place, untouched.
3. Agent rewrites `acceptance.md` — moves its own goalpost.
4. Agent signs the new `oracleMessage(root)` with its own key, drops the result
   in as `gate1.sig`.
5. `check-advanced-spec.js` prints **`Gate 1 protected: principal=rig-bot`** and
   exits 0.

Nothing failed. Nothing was deleted. The owner's key is still in the file.

## What this does to the previous two turns

- **Turn 2's claim that the pinned key is "the one artifact the agent cannot
  satisfy" was overstated.** The pin lives in a repo file the implementation
  agent can write. It is a **tripwire**, not a lock — and with list semantics
  the tripwire does not even trip, because forging requires no edit to the
  owner's line.
- **The owner is right on the substance they raised.** There is one signer,
  forever. No roster, no revocation, no roles. Multi-principal support buys
  nothing and is precisely what makes the forgery invisible. "Access control we
  do not need" is an accurate description of the *list*.
- **The owner's proposed remedy still fails.** "Any key not generated by the
  agent" is not a checkable property. A public key carries no provenance — there
  is no bit distinguishing a key made on the owner's laptop from one made by
  `ssh-keygen -t ed25519` in the agent's shell. Pinning the specific key *is* the
  implementation of "not agent-generated"; it is not an extra feature layered on
  top. Dropping the pin does not weaken the gate, it deletes it.

So both prior positions were half right. The correct move is neither "preserve
the comments" (turn 1) nor "drop the pin" (turn 2's owner ask): it is **collapse
the list to exactly one pinned principal and make anything else a hard failure.**

## Independent copies of the pin (why the tripwire has teeth)

The current fingerprint `SHA256:MYPMlpxH/cY5SGPoD2ghrL48SLoU5thTvRfViN8gdA4` is
recorded outside `gate1.allowed-signers`, in git history and in several wiki
notes (`2026-09-02-gate1-key-rotation-not-adopted.md`,
`2026-08-31-rig-154-close-out.md`, the QA/prod deploy review). A key swap is
therefore detectable after the fact by comparison. That redundancy is what makes
an in-repo pin worth keeping at all — and it also means the five `# key-class:`
comment lines are **not** the only copy of that provenance.

## Revised proposal

One change, covering the original comment-clobber defect and this one:

1. `gate1.allowed-signers` becomes a **purely generated single-principal file** —
   one line, no comments. Nothing to clobber; the comment defect disappears
   rather than being coded around. Provenance stays in `wiki/topics/gate1-signing.md`,
   which already carries it in full.
2. **The verifier stops looping.** It requires exactly one principal, and that
   principal must be `gate1-owner`. Any additional or foreign principal line is a
   hard failure with a loud message — not a silently-skipped candidate.
3. **The ceremony refuses** to overwrite a signers file that contains a principal
   other than `gate1-owner` (carried from turn 1, D2), so an agent-appended line
   is surfaced at signing time too.

Item 2 is the security fix and is new to this turn. Items 1 and 3 were already
on the table.

## Residual weakness (named, not fixed here)

Even after this, an agent that rewrites *both* `gate1.allowed-signers` and
`gate1.sig` in one go passes the verifier. The defence is that the pinned
fingerprint then changes, which is a conspicuous one-line diff in a file that
otherwise never changes, cross-checkable against the copies listed above. Making
it a true lock means anchoring the expected fingerprint somewhere the agent
cannot write (CI secret, signed tag, or the owner's environment). Out of scope
for this fix; recorded so it is not mistaken for solved.
