# 03 — Central Rig corpus (D9)

Part of the [master plan](00-master-plan.md). **This is the spine.** Subplans
04–09 build on it.

**Owner decision (round 5):** build it on this branch. All original 115 catalogue
capabilities live in the corpus and ship from it; compatible duplicate merges
may reduce the published service count. The user's agent unpacks it by following
clear onboarding instructions that ship inside the corpus. Never scope or test
per host.

Design source: [2026-09-08 brainstorm](../../reasoning/2026-09-08-dynamic-offboarding-architecture-brainstorm.md),
plus two feasibility results. Unknown-host projection by an agent worked for
Cursor and Zed. An agent-written deterministic projection script also worked.

  `scripts/check-rule-copies.js` exists only to police those copies.
- **The installer is static.** `rig/manifest.json` has 72 rows, most of them
  per-host `copy` rows. `rig/lib/payload.js` (694 lines) runs them, and
  `rig/lib/host-capabilities.js` holds a 19-host `REGISTRY`.
- **The adaptive path already exists.** `rig/lib/onboarding.js` (929 lines)
  runs propose→approve→apply→check, with the signed-proposal and journaling
  hardening landed.
- **The catalogue is separate.** It has 115 services as 805 templated files
  under `rig/catalog/services/`, plus a 55-SKILL.md third-party shelf (6.9 MB)
  under `rig/catalog/skills/`.
- **There is dead code.** `materializeSelectedHosts`

## Target shape

```
rig/corpus/                  ← the one source (owner selected one new root)
  skills/<name>/SKILL.md     ← one copy of each Rig skill
  rules/                     ← implementation + communication rules
  routing.md
  services/<family>/<group>/<service>/   ← finished catalogue (approved merges in 04)
  standards/                 ← AI development standards (subplan 07)
  upstream/                  ← pinned fetch metadata, licences and local patches
  onboarding/                ← the agent's unpacking instructions (below)
  projections/<host>.js      ← deterministic projectors for known hosts
```

Installed into a user repo as `.rig/` (the corpus, unchanged) plus host files
**generated** from it.

## Third-party delivery (owner decision)

Fetch selected upstream skills during onboarding. Keep upstream locations, pinned
revision, expected digest, licence/provenance and necessary local patches in
the corpus. Download to staging; verify before using approved fetched bytes.
Failed/unavailable downloads produce a named gap, never a successful install
of a missing capability. Fixtures cover invalid digests, unavailable upstream,
licence retention and patched browse-runtime behavior. Reconcile vendored
source changes with the frozen bundle and generated skill catalogue.

## Approach — Expand → Migrate → Contract

1. **Expand.** Create `rig/corpus/` from the current canonical copies:
   `rig/tier-1/*` and `rig/catalog/services`. Add
   `project(corpus, host, selection) → [{path, bytes}]`, a pure function, plus
   one projector per host the current manifest already serves. A test asserts
   that `project` reproduces **today's installed bytes** for every currently
   served host. That is the safety net.
2. **Migrate.** `payload.js` stops reading per-host copy rows and calls
   `project`. `onboarding.js` calls the same `project` when the agent selects
   skills. The six repo-root rule copies and `.claude/skills/` /
   `.agents/skills/` in **this** repo are regenerated by
   `node scripts/project-repo.js`. The stale markdown-only line in the
   canonical rule body is fixed here once, and all projections follow it.
3. **Contract.** Delete the checked-in twins, the per-host copy rows,
   `check-rule-copies.js` (replaced by "the projection is reproducible" plus a
   "no checked-in twin" uniqueness test), and `materializeSelectedHosts`.
4. **Unknown hosts.** `rig/corpus/onboarding/unpack.md` tells the user's agent
   how to project the corpus for a host with no projector: read the corpus,
   read the host's conventions, write a deterministic projection script, run it
   through propose→approve→apply→check, and offer the script back as a new
   projector.
5. **Onboarding instructions.** `rig/corpus/onboarding/` holds the
   step-by-step the agent follows: inspect the repo, select capabilities
   (including services), project, graft into existing config inside managed
   sections, verify. This **replaces** the per-host install prose in the README
   and routing.
6. **v5 migration.** Define the actual upgrade CLI and re-install path; both
   validate the journal and stage the corpus before changing the target. A
   journaled, resumable transaction retires only attributable v5 content,
   applies approved projections, and retains original preimages until success.
   An uninstall best-effort result stops migration with a recoverable report;
   it is never permission to overwrite an edited owned file. User content and
   original graft preimages survive upgrade and subsequent uninstall.
   Migrate `.rig/state.json` and selection receipts as well as journaled files.
   Preserve valid selections; invalidate old proposal approvals, applied and
   checked results when their bytes change. An already-checked v5 install
   cannot take the old apply early return and claim v6 was applied.
   Exercise interrupted removal/write, retry, corrupt journals, modified
   owned files, edited grafts, and symlink conflicts, as well as the happy path.

## Trust boundary

- Projectors that ship with Rig are pure functions: no I/O, no network.
- Agent-written projection scripts require approval and an actual filesystem
  and network sandbox, with repository input read-only and a dedicated output
  directory. `spawn-guarded` supplies process cleanup, not either sandbox.
  Refuse execution with a named reason if enforcement is unavailable.
- Scripts emit proposed `{path, bytes}` artifacts. Validate every artifact
  against approved paths, sizes and realpath/symlink containment, then apply
  through the existing journal writer. Scripts cannot mutate the target
  directly or choose new writes after approval.
- The proposal records the script's digest, so a modified script fails the
  apply step's digest check (reusing the signed-proposal hardening).

## Acceptance (observable)

1. **Reproducible:** for every host the v5 manifest served, the installed bytes
   from `project` equal the v5 installer's output, except for intended text
   and intended delivery changes, each listed explicitly. Projection parity
   checks canonical Rig bytes; fetched resources have separately pinned
   provenance/digests and do not silently inherit old vendored-copy expectations.
2. **Unique:** no file under `rig/corpus/` has a byte-identical twin anywhere
   else in the repo outside generated install output (RIG-132).
3. **One authority:** the MCP descriptor and the write path read one table, and
   an equivalence test over every projector agrees (the RIG-125 property).
4. **Round trip:** define uninstall evidence output outside the target or
   narrowly remove only this session's generated evidence. Compare a complete
   pre/post file inventory and bytes, including untracked and ignored content.
   Existing user reports survive; broad `--purge` is not the preservation test.
5. **Printed onboarding works:** the onboarding steps printed by install run to
   a green `check` (the RIG-125 property).
6. **Unknown host:** with a host name no projector knows, onboarding produces a
   proposal containing an agent-script slot, refuses to apply without approval,
   and applies approved artifacts after approval (RIG-110 reframed per
   North star 1). Adversarial scripts cannot write outside the sandbox,
   change an unapproved repository file, access the network, or substitute
   approved script bytes; missing isolation refuses before execution.
7. **Migration:** a v5-installed fixture repo upgraded to the corpus ends with
   corpus output, no v5 orphans, and user content intact.
8. Properties 3–5 are promoted into the frozen contract (RIG-125 "finish"),
   signed at [10](10-review-sign-ship.md).

## Frozen-contract impact

Frozen tests that read moved source paths are listed with their exact diffs in
an unfreeze bundle (master plan §6). Projection keeps installed paths stable,
but source APIs, service assertions and signed package plumbing also need
explicit amendment review; installed-output equality alone is insufficient.

## Risks

- **Silent output drift.** Mitigated by acceptance 1, which compares bytes
  before anything is deleted.
- **Hidden readers of old paths** (scripts, docs, tests). Before Contract, grep
  every old path and require zero hits outside the migration shim.
