# RIG-135 local patches against pinned upstream bytes

Third-party browse sources are fetched during onboarding from a pinned
upstream revision; Rig keeps tested local patches, the licence notice
(`rig/catalog/skills/LICENSE.upstream`, MIT) and provenance. Patch files live
beside this note in `rig-135/`, in `git diff` form relative to repository root.

- Upstream: `garrytan/gstack` 1.60.1.0, release commit
  `7c9df1c568a9ea745508f679a329332b2c338063` (see `rig/catalog/skills/UPSTREAM.md`).
- Vendored path: `rig/catalog/skills/browser-and-research/browser-automation/browse/src/<file>`
  (upstream path `browse/src/<file>`; Rig renamed the product namespace on import).
- Base digest: sha256 of the vendored file at the commit before the patch. The
  vendored bytes are already a Rig-modified import, so the pure-upstream digest
  is whatever the onboarding fetch pins; the patch must be re-verified against
  that digest when the fetch pipeline lands.
- `src/process-tree.ts` is a new Rig-authored file (no upstream counterpart).
- The spawn-guard allowlist (`rig/spawn-guard-allowlist.json`) and its test were
  not frozen (absent from `wiki/gate1/testing-infrastructure.manifest`), so the
  RIG-135.2 entry was removed directly.

Deviation, 135.1: no native Windows Job Object. Node/Bun expose none and an FFI
binding could not be verified without Windows. The spec's alternative is used:
`taskkill /T /F` tree kill on every exit path plus an OS-level watchdog (a
sibling process holding the read end of a pipe; the OS closes the pipe if the
importer dies, and the watchdog then kills the tree). Known limit: `taskkill /T`
follows parent links, so a descendant whose parent already exited is not reached.
