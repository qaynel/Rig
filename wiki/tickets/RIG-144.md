## Owner sign-off, with three corrections (2026-08-29)

Owner approved the draft with three changes and one addition. Full
reasoning: [[reasoning/2026-08-29-rig144-capability-policy-sign-off]].

1. **Network is three states, not two.** `network: none` (explicit deny) and
   `network: required` (explicit allow) are enforced immediately. An
   undeclared binding keeps running for now (still the additive rollout,
   avoiding silent breakage of the ~115 legacy catalog packs) but must emit a
   visible diagnostic and be recorded as its own distinct state — never
   silently folded into "allowed" — so a later release can flip
   `undeclared -> deny` without a schema change.
2. **The two runners are unified, not just drift-tested — rejected as the
   draft's biggest under-scoping.** "A drift test changes silent divergence
   into divergence noticed by CI. Better, but the defect class still
   exists." `.rig/bin/check.js` may remain a physical installed file, but it
   must be a generated/copied artifact of one canonical source, not a second
   file a human hand-edits. **Done this session, first, ahead of the rest of
   this ticket:** the shared `runArgv`/`runBinding` logic moved into
   `rig/lib/check-runner.js`; both `rig/lib/checks.js` and
   `rig/catalog/baseline/check.js` now `require()` it instead of each
   carrying their own copy; `apply.js` materializes it into `.rig/lib/`
   alongside `path-safety.js`/`spawn-guarded.js`. `AT-CAP-6` (new,
   `tests/guarantee-coverage.test.js`) asserts object identity between the
   two callers' `runBinding`, not just matching behavior — a hand-copied
   `runBinding` creeping back in now fails this test immediately. Confirmed
   green: 18/18 in `tests/guarantee-coverage.test.js`, including the
   rewritten `AT-PROC-1p` (updated to the canonical result shape).
3. **CI authority is committed-policy-or-refuse, no fake approval.** No
   ephemeral approval environment variable, no implicit yes, no prompting —
   an explicit `.rig/execution-policy.json` entry is the only way to
   authorize a capability beyond default on this non-interactive path,
   structured as a shared capability evaluator so a later interactive
   one-use-grant path authorizes through the same evaluator rather than a
   second bespoke mechanism.
4. **Addition: resource ceilings are configurable defaults, not hard
   limits.** `10 min / 2 GiB` are defaults; the invariant is
   `0 < t_command <= t_authorised` and `0 < M_command <= M_authorised`, a
   binding may declare a higher authorised ceiling, and timeout kill must
   cover the whole descendant process tree (already true via
   `spawnGuardedSync`).

**Implemented after the approved design check:** `AT-CAP-1`/`2` apply
configurable default resource ceilings through the existing watchdog;
`AT-CAP-3` enforces explicit network denial, explicit required access, and a
visible undeclared state; `AT-CAP-4` uses the committed exact-service

## Problem

`rig/lib/lint-format.js`'s command runner (`runReadOnly`/`runGrade`/
`runCommand`) carries the full shell-trust guarantee set closing
[[RIG-115]]/[[RIG-137]]/[[RIG-138]]/[[RIG-139]]/[[RIG-140]]: durable one-use
plan approval, realpath-based fs/cwd containment, default-deny network
reachability, a polling memory ceiling, and wall-clock timeout kill-and-report.

`rig/catalog/baseline/check.js` (materialized into a target repo as
`.rig/bin/check.js`, the CI/git floor runner) is a separate, simpler command
runner for the same class of problem — running externally-declared commands
against a repository — and has **none** of that hardening:

- No plan/approval concept at all; commands run as soon as `runBinding` is
  reached, with no one-use consumption analogous to AT-LF-20.
- `cwd` containment (`runBinding`'s `commandBinding.cwd` check, lines ~70-75)
  is a `path.resolve` + `startsWith(repoRoot + path.sep)` string check, not
  the realpath-based symlink-aware containment `taskCwd`/`containedPath` use
  elsewhere — a symlinked directory inside the repo that resolves outside it
  would pass this check.
- No network isolation prefix (AT-LF-22): every check command runs with full
  network reachability, granted or not.
- No memory ceiling (AT-LF-23/RIG-140): a runaway check command can OOM the
  host.
- It does already use `spawnGuardedSync` (RIG-135's group-kill helper), so
  process-tree cleanup on the bare `timeout: 10 * 60 * 1000` is covered; that
  axis is not part of this ticket.

## Why this isn't a drop-in port

This runner's execution model differs from `lint-format.js`'s in ways that
matter for which guarantees actually apply:

- It runs **CI/git-floor checks** (`npm test`, linters, the repo's own
  declared commands) — these routinely *need* network access (package
  installs, registry checks) and can legitimately run long or allocate a lot
  of memory for a large repo's real test suite. Applying AT-LF-22's
  default-deny network stance or a fixed memory ceiling here could break
  ordinary, legitimate CI runs rather than protect against anything.
  Sonnet-plausible.
- It has no plan/execute split — there's no "approve now, execute later"
  seam for a one-use approval to attach to.

## What needs an owner decision before implementation

1. Which of AT-LF-20..24 actually apply to this execution model, and which
   are inapplicable by design (not merely unported)?
2. If cwd containment should be hardened to realpath-based checks (this one
   looks unambiguously worth doing regardless of the other four — it's a
   pure correctness gap, not a policy tradeoff).
3. Whether a per-service, repo-declared `network`/`memory_limit_mb` opt-in
   (mirroring `cmd.network` / `cmd.memory_limit_mb` in `lint-format.js`)
   is the right shape here, or whether that duplicates policy that should
   live in `rig/catalog/baseline/services.json` bindings instead.
