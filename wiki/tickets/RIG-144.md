# RIG-144 — Installed `rig/catalog/baseline/check.js` carries none of the AT-LF-20..24 hardening

**Class: CORRECTNESS / SHELL TRUST — target-repo-facing, needs owner scoping.**
**Status: OPEN (2026-08-28) — GitHub #104 — filed from the PR #83 non-gating triage list.**
Ticket: RIG-144 on [[Tickets]].

## Problem

`rig/lib/lint-format.js`'s command runner (`runReadOnly`/`runGrade`/
`runCommand`) carries the full shell-trust guarantee set closing
[[RIG-115]]/[[RIG-137]]/[[RIG-138]]/[[RIG-139]]/[[RIG-140]]: durable one-use
plan approval, realpath-based fs/cwd containment, default-deny network
reachability, a polling memory ceiling, and wall-clock timeout kill-and-report.

`rig/catalog/baseline/check.js` (materialized into a target repo as
`.rig/bin/check.js`, the CI/git floor runner) is a separate, simpler command
runner for the same class of problem — running externally-declared commands
against a repository — and has **none** of that hardening:

- No plan/approval concept at all; commands run as soon as `runBinding` is
  reached, with no one-use consumption analogous to AT-LF-20.
- `cwd` containment (`runBinding`'s `commandBinding.cwd` check, lines ~70-75)
  is a `path.resolve` + `startsWith(repoRoot + path.sep)` string check, not
  the realpath-based symlink-aware containment `taskCwd`/`containedPath` use
  elsewhere — a symlinked directory inside the repo that resolves outside it
  would pass this check.
- No network isolation prefix (AT-LF-22): every check command runs with full
  network reachability, granted or not.
- No memory ceiling (AT-LF-23/RIG-140): a runaway check command can OOM the
  host.
- It does already use `spawnGuardedSync` (RIG-135's group-kill helper), so
  process-tree cleanup on the bare `timeout: 10 * 60 * 1000` is covered; that
  axis is not part of this ticket.

## Why this isn't a drop-in port

This runner's execution model differs from `lint-format.js`'s in ways that
matter for which guarantees actually apply:

- It runs **CI/git-floor checks** (`npm test`, linters, the repo's own
  declared commands) — these routinely *need* network access (package
  installs, registry checks) and can legitimately run long or allocate a lot
  of memory for a large repo's real test suite. Applying AT-LF-22's
  default-deny network stance or a fixed memory ceiling here could break
  ordinary, legitimate CI runs rather than protect against anything.
  Sonnet-plausible.
- It has no plan/execute split — there's no "approve now, execute later"
  seam for a one-use approval to attach to.

## What needs an owner decision before implementation

1. Which of AT-LF-20..24 actually apply to this execution model, and which
   are inapplicable by design (not merely unported)?
2. If cwd containment should be hardened to realpath-based checks (this one
   looks unambiguously worth doing regardless of the other four — it's a
   pure correctness gap, not a policy tradeoff).
3. Whether a per-service, repo-declared `network`/`memory_limit_mb` opt-in
   (mirroring `cmd.network` / `cmd.memory_limit_mb` in `lint-format.js`)
   is the right shape here, or whether that duplicates policy that should
   live in `rig/catalog/baseline/services.json` bindings instead.

## Acceptance (draft — not yet reviewed or signed off)

- `runBinding`'s cwd/required-path containment is realpath-based, closing the
  symlink-escape gap, regardless of how the network/memory questions above
  resolve.
- Whatever subset of network isolation / memory ceiling the owner scopes in
  is named and tested the same way `AT-LF-22`/`AT-LF-23` are (a distinct,
  non-passing, non-silent status).
- A new test title covers each behavior actually implemented, in a file
  outside the frozen `wiki/gate1/testing-infrastructure.manifest` unless the
  owner explicitly wants this promoted into the signed oracle.

Not implemented in this pass — recorded per the "resolve or record" triage
item, since the network/memory scope questions need owner input the way
RIG-135.1/.2/.3's Bun group-kill gap did.
