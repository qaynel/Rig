# RIG-141 — runReadOnly hard-refuses all tasks when sandbox absent; granted-network path untested

**Class: CORRECTNESS / SHELL TRUST.**
**Status: COMPLETE (2026-08-27) — GitHub #96.**
Ticket: RIG-141 on [[Tickets]].

## Problem

AT-LF-22 requires: deny outbound network to ungranted tasks. It does not require
refusing all execution when the sandboxing tool is absent.

`runReadOnly` currently does:

```js
function runReadOnly(target, commands) {
  const isolation = networkIsolationPrefix();
  if (!isolation) {
    console.warn('runReadOnly: network isolation unavailable; skipping read-only tasks');
    return { status: 'network_isolation_unavailable' };
  }
```

When `unshare` (Linux) or `sandbox-exec` (macOS) is absent, every task is
refused — including tasks where `cmd.network === true` (explicitly granted
network access). `argvWithNetworkIsolation` already skips the prefix for granted
tasks (`if (cmd.network === true) return argv`), but the early return fires
before that logic is reached.

**Two distinct gaps:**

1. **Over-blocking:** A task with an explicit network grant is refused when the
   sandbox tool is absent, even though AT-LF-22 says nothing about blocking
   granted tasks. The spec allows them; the code refuses them.
2. **No test coverage:** The `cmd.network === true` execution path has zero test
   coverage anywhere. The granted half of AT-LF-22 is completely untested.

## Location

`rig/lib/lint-format.js`:
- `runReadOnly`, lines 606–611 — the early-return block that over-blocks
- `argvWithNetworkIsolation`, lines 600–604 — the correct grant bypass, currently unreachable from the above

## Required fix shape

When the sandbox tool is absent:
- Tasks with `cmd.network !== true`: still return a non-passing status
  (`network_isolation_unavailable`). Cannot safely run without isolation.
- Tasks with `cmd.network === true`: proceed. No isolation needed; no refusal warranted.

A new acceptance case must cover the granted-network execution path before
implementation.

## Acceptance

- A task with `cmd.network === true` runs and returns `clean` even when no
  sandbox tool is present on the host.
- A task with no explicit grant still returns `network_isolation_unavailable`
  when the sandbox tool is absent (existing behaviour preserved).
- Named tests covering both paths are in `tests/advanced-oracle.test.js`:
  `RIG-141 granted-network task runs when no sandbox tool is present` and
  `RIG-141 ungranted task still refuses when no sandbox tool is present`.
- The existing AT-LF-22 ungranted-denial test is unaffected.

Tests are implemented (2026-08-27). They were RED against the current buggy
code on `rig-115-at-lf-22-network-denial` and are GREEN after the fix.

Implementation is complete: the network-isolation refusal is now gated per
command, so explicitly granted tasks can run without a sandbox tool while
ungranted tasks retain the refusal.
