## Follow-up — RIG-124.1 (Important, found 2026-08-26, fixed 2026-08-26 — GitHub #73)

**A killed/timed-out reviewer attempt is silently dropped from the re-review
cap instead of counting toward it.** `scripts/review-receipt.js` persists the
failure count to `<out>.attempts.json` only at lines 184-188, *after* the
reviewer subprocess spawn (line 162, `timeout: TIMEOUT_MS` = 30 minutes)
returns cleanly. If that spawn is killed by its own timeout — or any other
signal — before returning, `run.status !== 0` triggers `fail()` at line 171
and the process exits before ever reaching the write. The prior failure count
on disk is left stale (too low), so the next attempt for the same
`author-context` reads an undercount, is not capped, and gets an extra, silent
retry beyond the intended "one re-review" limit.

Found while investigating why the RIG-120 release-ceremony `npm test` gate
went red on `tests/release-blockers.test.js`'s
`review-receipt cap is scoped per author-context and clears on a passing
verdict (RIG-124)` (`capped.invocationCount` read `1` instead of the expected
`0`), after a run whose total duration (~1,800,952ms) landed within ~1s of
`TIMEOUT_MS` (1,800,000ms) — strong evidence a reviewer subprocess spawn
genuinely hit that internal timeout and got killed mid-attempt. The failure
does not reproduce in isolation (`node --test tests/release-blockers.test.js`
is 34/34 green in 16s) or under repeated single-file runs; it is a timing-
dependent lost-update, not a logic bug in the steady-state path. Deterministic
repro (bypassing the need for a real 30-minute hang) and full trace:
[[2026-08-26-rig124-cap-lost-update]].

**Why it matters:** RIG-124 exists specifically to bound automatic
retry/re-review loops around the release gate. A reviewer subprocess timing
out is exactly the "stuck/expensive call" scenario RIG-124 was built to cap —
and it is the one scenario where the cap currently fails open instead of
closed. This sits directly on the RIG-120 release-ceremony path: a real
`review-receipt.js` invocation against a live model that times out would hit
this same gap.

**Fix direction:** persist a failure record before spawning the reviewer
(optimistic write), then clear/confirm it only on a definite outcome — or
otherwise make the counter increment on any non-clean return (timeout, signal,
launch error), not only on a parsed `fail` verdict. Add a regression test that
forces the reviewer spawn to time out or be killed mid-attempt and asserts the
next same-context attempt is still capped.

**Second, related gap found chasing why the triggering run took the full
timeout** (see addendum in [[2026-08-26-rig124-timeout-duration-investigation]]):
killing the reviewer spawn only terminates that one tracked process, not any
child process it had already forked. Confirmed directly — a script blocked
waiting on its own child dies on the timeout signal as expected, but the
child survives, orphaned, running indefinitely. The real reviewer is a full
agent that plausibly forks its own children while working; on the same kill
path, a review the wrapper believes it cancelled may keep running
unsupervised. Fix direction: spawn the reviewer in its own process group and
signal the whole group on timeout/kill, not just the tracked process, so a
cancelled review is guaranteed to actually stop.

**Scope decision (2026-08-26):** fixed narrowly, inside `review-receipt.js`
only — a shared, guaranteed-cleanup helper for every subprocess this tool
spawns anywhere is a separate, deliberately independent change, filed as
[[RIG-135]] (GitHub #75) rather than folded into this fix.

**Acceptance (owner-approved 2026-08-26, both implemented and tested):**
- A reviewer subprocess that times out or is killed before returning counts as
  a failure toward the same-`author-context` cap.
  → `scripts/review-receipt.js` now writes the failure record *before*
  spawning the reviewer (optimistic write) and only clears it on a confirmed
  `pass`; a killed/timed-out/non-clean return leaves the count in place.
  → tests/release-blockers.test.js::review-receipt counts a killed/timed-out reviewer spawn toward the re-review cap (RIG-124.1)
- Killing the reviewer spawn (timeout or otherwise) leaves no descendant
  process still running afterward.
  → the reviewer now spawns `detached: true` (its own process group); right
  after `spawnSync` returns, `review-receipt.js` signals the whole group
  (`process.kill(-run.pid, 'SIGKILL')`), not just the one tracked process.
  → tests/release-blockers.test.js::killing a hung reviewer spawn leaves no descendant process still running (RIG-124.1)

Both regression tests were confirmed to fail against the pre-fix code (one by
under-counting the cap, one by timing out entirely because a leaked
grandchild process was never reaped) before the fix landed, and pass with it
in place. A test-only `RIG_REVIEW_RECEIPT_TIMEOUT_MS` env override lets the
tests force the real timeout path in milliseconds instead of the production
30-minute `TIMEOUT_MS`.

## Problem

Substantial-but-routine tasks exhaust the 5h/weekly account limit. Three pasted
session transcripts (`.context/attachments/`, see
[[2026-08-25-token-burn-investigation]]) show the cost is **tool-call volume and
nested model spawns, not context-window pressure** — no session hit a context
wall; they hit the account rate limit. Three multipliers, ranked:

1. **Nested reviewer retry loop.** `scripts/review-receipt.js` (`spawnSync`,
   30-min timeout, `review-receipt.js:18-22`) launches a *second full model* to
   review the whole diff. When it returned `verdict: fail`, the agent fixed the
   finding and re-ran the review — **three full nested-review cycles in one turn**
   (528fiH lines 262, 646, 840), each interleaved with a full gate run.
2. **Full-gate `npm test` as the inner loop** — 6–7 runs per session (the entire
   CI gate incl. the `.venv`/pandas benchmark), used as the red/green step, while
   the documented fast subset `npm run test:rig` sat unused.
3. **Per-turn instruction tax.** CLAUDE.md tells every agent — even for a one-line
   ask — to re-read `routing.md`, read the wiki, read each chosen skill *in full*,
   and rewrite the wiki every 3 minutes. Correct for long work; a flat tax on small
   work, and it compounds on every resume.

## Proposed resolution

Three independent changes; can land separately.

1. **Cap the nested reviewer.** A `fail` verdict is real signal — stop and surface
   it, never silently re-review. Limit re-reviews to **one**. Use a cheap model
   (Haiku/Sonnet) for interim passes and reserve the expensive model for the final
   receipt. It is a **release-only** gate — never run mid-development. Enforce the
   cap where possible (a guard/env in `review-receipt.js` or the release skill)
   rather than relying on agent discipline alone.
2. **Inner-loop test discipline.** During red/green, run `npm run test:rig` or the
   single relevant test file. Full `npm test` runs **once**, right before push.
   Encode this in the implementation/tdd guidance so agents stop using the full
   gate as the inner loop.
3. **Scope the per-turn tax.** Make "read the full skill / update wiki every 3 min
   / re-read routing" apply to **multi-step** work, not every small ask. Adjust
   CLAUDE.md and `routing.md` so a single-file/one-liner has a lighter path.

## Design note / oracle intersection

Change 1 touches the release-review contract (AT-GATE-3 "fresh reviewer session").
The *fresh-session* requirement stays; only the auto-retry and interim-model choice
change. **Resolved: no re-sign needed** — neither `scripts/review-receipt.js`
nor `rig/lib/release-evidence.js` is in `wiki/gate1/testing-infrastructure.manifest`,
and the frozen `AT-GATE-3` test only exercises `validateReviewReceipt`'s
fresh-session/report-only/digest contract, not the wrapper's CLI or retry
count. Verified the frozen test still passes unmodified. Changes 2 and 3 are
instruction/policy only, as expected.
