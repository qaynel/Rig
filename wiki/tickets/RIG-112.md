# RIG-112 — Freeze and implement the catalogue contract + authored-service gate

**Status: FREEZE QUESTION CLOSED (2026-08-24) — no freeze now, by doctrine.**
Ticket: RIG-112 on [[Tickets]].

## Resolution (owner, 2026-08-24)
The "freeze now?" half was a **mis-raised question**, generated by reading the
descriptive line "designed but not frozen" in `topics/catalogue-contract.md` as
an outstanding action. By doctrine ([D27](../index/decisions.md),
[the gate](../topics/the-two-gates.md)) nothing locks until its solution,
acceptance, and tests are all in place and the owner agrees — "not frozen" is the
normal pre-freeze default, not a decision. **So: no freeze.** The mechanical
CI-over-115 confirmation and any stronger specificity heuristic proceed under the
ordinary gate (below). The catalogue contract freezes only later, as an ordinary
end-of-pipeline step, once its acceptance + tests exist and the owner agrees.
See the [process doctrine trace](../reasoning/2026-08-24-process-doctrine-and-one-lock.md).

## Problem
The catalogue-contract topic says the contract is "designed but not frozen or
implemented," and the authored-service gate "must later prove that mechanically
valid leaves also carry real, service-specific meaning." All 115 leaves are
authored at Policy grade, but nothing yet proves a leaf's policy/checks are
genuinely service-specific rather than well-formed boilerplate.

## Findings (verified — corrects part of the ticket)
The **mechanical** authored-service gate already exists and is green
(`topics/authored-service-gate.md`): it opens every declared file and rejects
missing/empty markdown, placeholders, the old boilerplate phrases, generic
`core/extended/thorough` check IDs, omitted owned/applicability/disposition
metadata, missing grade checks, and duplicate bodies; an unbound generic Policy
service is a named nonzero coverage gap (not `exit 0`). So "the gate does not
exist" is stale. Two things genuinely remain:
1. The **catalogue contract itself is not frozen** — Gate 2 §5 is the working
   spec, present not locked. Freezing it edits the signed oracle.
2. The **semantic** half — proving service-specific *meaning*, not just
   mechanical validity — is today a "fresh exact-digest semantic review" done as
   a release operation, not an automated CI gate over all 115.

## Solution
1. **Confirm/extend CI coverage over all 115 leaves.** Verify the mechanical
   gate runs across the full catalogue in `npm test` (it is invoked via the
   advanced suite); if any family is unscanned, extend the gate's file
   enumeration and add a count assertion (`== 115`). This part is landable now.
2. **Add a stronger service-specificity check** where mechanizable: e.g. every
   leaf's checks must reference at least one repository-derived binding or a
   service-named artifact (not only prose), failing a mechanically-valid but
   generic leaf as a coverage gap — the acceptance's core ask.
3. **Freeze the contract** (owner operation): once §5 is stable, add the
   catalogue-contract artifacts to the Gate 1 signed set and re-sign
   (non-delegable, same mechanism as [[RIG-102]]). The semantic exact-digest
   review remains an owner release step ([[RIG-120]]).

## Owner input
Contract freeze + any acceptance change is a re-signing ceremony. The mechanical
CI-over-115 confirmation and the stronger specificity heuristic can be drafted
and landed under the ordinary gate first.
