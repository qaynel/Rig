# RIG-145 — runReadOnly batch-aborts the command list on isolation-unavailable where runGrade marks per command

**Class: CORRECTNESS / SHELL TRUST (parity).**
**Status: OPEN (2026-08-29) — GitHub #108 — accepted follow-up from the passing v5.0.0 review; non-blocking.**
Ticket: RIG-145 on [[Tickets]].

## Problem

`runReadOnly` (`rig/lib/lint-format.js:696-700`) does a function-level
`return { status: 'network_isolation_unavailable' }` the moment it meets the
first command that has no network grant while no OS isolation prefix is
available. Every later command in the same plan is skipped — including one
with `network: true` that `runGrade` **would** run, because `runGrade`'s
identical check (`:627-628`) lives inside its `.map` and returns a
per-command result instead of aborting the batch.

This is the same guarantee-sharding pattern already fixed for the cwd axis
([[RIG-139]]) and the network-isolation axis on the grade path ([[RIG-143]]):
the two runners are supposed to be at parity, and `tests/guarantee-coverage.test.js`
asserts that parity per axis (`AT-PROC-1b`/`1d`). This axis — batch vs
per-command handling of an ungrantable command — is still asymmetric. See
[[mistakes/guarantee-sharding]].

Not a safety hole: nothing ungranted executes. It is an availability/parity
gap — a legitimately `network: true`-granted command is silently skipped and
the whole plan reports `network_isolation_unavailable`.

Secondary nit at the same site: this early return omits `changed_paths`,
unlike every other early return in `runReadOnly`.

## Location

`rig/lib/lint-format.js`:
- `runReadOnly` (`:692-726`) — the batch-abort `return` at `:696-700`.
- `runGrade` (`:609-667`) — the per-command reference at `:627-628`, inside
  `.map`.
- `argvWithNetworkIsolation` (`:686-690`) — shared, unchanged.

## Reachability

Neither `runReadOnly` nor `runGrade` has a non-test caller in `rig/` today
(grep confirms only test/comment references), so this is latent, exactly as
[[RIG-143]] was when filed. It bites only on a host with no `unshare` /
`sandbox-exec` running a multi-command read-only plan whose first command is
ungranted and a later command is `network: true`.

## Required fix shape

- `runReadOnly` handles the ungrantable command per-command (skip it with a
  recorded non-passing state) and keeps running the granted commands that
  follow, mirroring `runGrade`.
- Reconcile a single batch status from the per-command outcomes — the change
  touches `runReadOnly`'s single-status return contract, so the exact shape
  (e.g. worst-status-wins, or a `commands[]` array like `runGrade`) is an
  owner decision.
- The isolation-unavailable early return includes `changed_paths` like its
  siblings.
- `tests/guarantee-coverage.test.js` gains an `AT-PROC-1` parity case:
  `[ungranted, network:true]` through `runReadOnly` on a host with no sandbox
  tool — the granted command runs; red against today's code, green after.
- No frozen file is edited; no oracle re-sign required.

## Acceptance

- A `runReadOnly` plan `[cmd0 (no grant), cmd1 (network: true)]` on a host
  with no isolation tool runs `cmd1` (parity with `runGrade`).
- `cmd0` is still reported as non-passing / isolation-unavailable; nothing
  ungranted reaches an outbound listener (existing `AT-LF-22` behaviour for
  ungranted commands preserved).
- The isolation-unavailable result carries `changed_paths`.
- New `AT-PROC-1` case added, red-before / green-after.
- No frozen file (`tests/advanced-oracle.test.js`,
  `wiki/gate1/testing-infrastructure.manifest`) edited.
