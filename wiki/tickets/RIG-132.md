## Problem

Every review finding this project has ever received — spec or code — has the same
grammar: **"this place says A, that place says B."** Consistency is a property of
a *pair*, not of a location.

The specification carries ~124 addressable claim anchors (79 numbered sections,
37 `AD-`, 68 `AT-`, 19 `D`), which is **~7,600 pairs**. A review pass reports
2–8 findings. Six rounds covered roughly 0.4% of the space. The receipt anchors
prove the mechanism directly: the same sections recur across rounds paired with
*different* partners each time — `§8.4` in rounds 3 and 5, `§11.3` and `§5.7` and
`§8.9` in rounds 4 and 5, `§13` four times in round 5 and again in round 6. §8.4
was not fixed wrong; it was reconciled with one partner and later found
inconsistent with another.

The code side is identical with implicit cross-references, and the git trace
shows the pairs long pre-date the passes that missed them — the second
uninstaller has been in the tree since **July 2026**, through every review the
project has run. Worse, two of the round-3 findings were introduced by commits
that were *themselves fixes for earlier findings* (`192f35e` "Unify MCP renderer
dispositions", `35fc852` RIG-107 wiring). A fix that adds a table or prints a new
command adds anchors, and anchors add pairs.

**So the finding pool is not static and not linear in the work. It is quadratic
in the number of places a fact can live, and every fix grows it.**

## The losing move, visible in one file

`scripts/check-rule-copies.js` guards seven byte-identical copies of the rule
body, cannot guard the eighth (`skills/rig/SKILL.md` is structurally different),
falls back to asserting eight hand-picked substrings, and carries this comment:

```
// Upgrade path: generate the copies from SKILL.md if this ever misses a real drift.
```

The correct fix is written down and not done. `check-versions.js` is the same
shape: *"Rig declares its version in seven files."*

A guard costs O(1) and covers exactly one pair someone already thought of. The
pairs are O(N²) and nobody thought of most of them. That is why every guard is
green while every review fails.

the right exponent.

## Why this precedes RIG-125

[[RIG-125]]'s property tests are the right instrument, but a property test is
still a guard over pairs somebody enumerated. Written over today's N they are a
sample; written over a collapsed N they are close to exhaustive and affordable.
Collapse first, then write them.

## Recommended direction

1. **Inventory as a manifest.** Check in the table above as data
   (`wiki/sources/duplicate-fact-inventory.json` or equivalent): fact, homes,
   guard, disposition (`collapse` / `generate` / `justified-twin`).
2. **Collapse the four unguarded rows first** — duplicated MCP server directory
   (make `rig/mcp-runtime/` a build/install copy of `rig-mcp/`, not a checked-in
   twin), one MCP disposition table, one uninstall authority, one onboarding
   path. The last three are [[RIG-125]] / [[RIG-127]] / [[RIG-126]] work; this
   ticket owns the framing and the first row.
3. **Generate the guarded rows** — rule copies and skill copies derive from one
   source at build/install time; delete the checked-in copies and their equality
   guards together. A guard that no longer has anything to guard is the success
   condition.
4. **New-twin check.** A `npm test` step that fails when a commit adds a
   byte-identical pair not declared `justified-twin` in the manifest. This is the
   standing rule: **new duplication ships with its generator, or it does not
   ship.**

## Acceptance

- The duplicate-fact manifest exists and lists every tracked byte-identical group
  with a disposition.
- `rig/mcp-runtime/` is no longer a checked-in twin of `rig-mcp/`; the install
  path derives it, and deleting one source cannot leave the other stale.
- Rule copies and skill copies are generated from their single source; the
  corresponding equality guards are deleted along with the copies they guarded.
- A commit that introduces an undeclared byte-identical twin fails `npm test`.
- The `justified-twin` count is printed on every run so exceptions stay visible
  rather than becoming the default.
- The `skills/rig/SKILL.md` substring-canary fallback is gone, because the copy
  it approximated no longer exists.
- **The semantic model, its interpreter and the generators are authoring/build
  concerns in this repository only.** No semantic-model runtime, resolver or
  config is emitted into a target repository — installs still land markdown and
  instruction files only. (Satisfies the standing Tier-1 markdown-only rule, and
  is the source analysis's fifth pre-v5 condition.)
- The raw-field allowlist is empty at the end of the Contract phase.

## Goal re-stated (2026-08-25, after the outside analysis)

**Retitled 2026-08-25.** "One home per fact" — the original framing — is not sufficient,
and this repo is the proof.

`REGISTRY` already *is* a single source of truth for hosts. `mcp-hosts.js`
derives `MCP_HOSTS` from it with `AUTO_WRITE_OVERRIDE`, `FILE_OVERRIDE` and
`LEGACY_FILE` applied. `materializeSelectedHosts` reads `caps.mcp_config` /
`caps.surfaces` off the same `REGISTRY` and applies none of them. One home, two
interpretations, divergent shipped behaviour, full gate green. Single-source-of-
truth was satisfied the entire time that bug existed.

A single authored source still permits every consumer to re-interpret the raw
facts:

```
registry.json → renderer A
registry.json → renderer B
registry.json → special host logic C
registry.json → weird exception D
```

The goal is therefore **one authority for the *meaning*, with every consumer
taking the interpreted result rather than the raw row** — a semantic model, with
runtime, docs and tests as generated projections through one narrow contract.
Established terms, not invented ones: *semantic model* / *model-aware
generation* (Fowler's DSL catalogue), *narrow waist* (the IETF hourglass — M×N
agreements become M+N conformances), *architectural fitness function*
(Ford/Parsons/Kua) for the ratchet.

Assessment of the source analysis, including what this project declines from it:
[[2026-08-25-semantic-model-assessment]]. Source held verbatim at
`sources/reference/normalized-semantic-architecture.raw.md` *(never landed in the repo)*.

**Scope discipline.** The source proposes seven numbered fitness functions, a
normative-intent layer and a name for the architecture. This ticket takes **two**
fitness functions — no second semantic authority (the ratchet below) and no
bypass of the host contract ([[RIG-125]]) — writes the rest as ordinary tests,
and does not name the architecture.
[[2026-08-20-first-attempt-retrospective]] lists over-engineered governance and
mechanism-before-leaf among the five named past mistakes; a de-duplication
programme that opens with a numbered regime has re-created them.

## The invariant, in its checkable form (2026-08-25)

Take this verbatim as the ticket's statement of intent:

> **Consumers may consume semantic results, but may not independently interpret
> semantic inputs.**

Bad:

```javascript
const host = REGISTRY[id];
if (host.mcp === ...)        // my interpretation
deriveAutoWriteMyOwnWay(host);
```

Good:

```javascript
const semantics = HostContract.resolve(id);
semantics.mcp.disposition
semantics.mcp.autoWrite
semantics.mcp.configPath
```

The raw model owns data. The semantic layer owns interpretation. Consumers own
neither. This is phrased as a **prohibition on a consumer**, which is what makes
it checkable — "one authority for the meaning" was not.

Two distinct things, and SSOT only ever addressed the first:

- **Canonical representation** — where is the input knowledge authored?
- **Semantic authority** — who is allowed to decide what it means?

**Branch by Abstraction** / **Parallel Change** migration, which keeps the system

**Pre-v5.0.0 (ships with the release):**

2. The **raw-field allowlist ratchet** lands — see the correction below.
3. The allowlist *is* the committed debt inventory; its count is printed.
4. [[RIG-134]]'s classification runs; every `v5-observable` defect is fixed as a

5. No semantic-model runtime enters target repositories.

**v5.1 (this ticket):**

- **Expand** — introduce `HostContract` reproducing today's established
  semantics exactly. No feature work, no new host format, no DSL. Installing the
  seam, at behaviour parity.
- **Migrate** — one interpretation at a time: MCP disposition → verify →
  auto-write → verify → config path → verify → lifecycle semantics. Full gate
  green and releasable at every step.
- **Contract** — delete the old paths once nothing uses them.

### Correction: the pre-v5 ratchet cannot reference `HostContract`

The source's Phase 0 prohibition is *"no new independent semantic interpretation
of host/domain facts"* — but `HostContract` does not exist until Expand, a phase
later, so as written the pre-v5 ratchet has nothing to point at.

Implementable form: **a grandfathered allowlist of the modules permitted to read
raw `REGISTRY` fields, which may only shrink.** A static check that no module
outside the allowlist destructures `mcp_config`, `surfaces`, `instruction` or the
other raw capability fields; adding a module fails CI. Checkable today, freezes
the debt at its current value while v5.0.0 ships, and during Migrate each
converted consumer is removed from the list — so **the allowlist is the
migration's progress bar.** When it empties, Contract is done.

### The allowlist and the debt inventory are one artefact

If the debt lands as a prose register *and* the ratchet keeps its own config, a
de-duplication programme has opened by duplicating a fact. One artefact: the
manifest is the inventory, the ratchet reads it, the count it prints is the
number reported.

## Low-context implementation packet — pre-v5 ratchet only

**Scope.** Do this release's small ratchet, not the v5.1 migration. Do not add
`HostContract`, move consumers, generate projections, or change target-repository
payloads. The release only freezes the number of consumers that independently
read raw host capability fields; later migration can make that count shrink.

**Chosen artifact.** Add `rig/raw-registry-access.json` as the one committed
debt inventory and allowlist. It contains a schema version, the current allowed
source files, the raw fields each may read, and the expected count. The current
semantic reader is `rig/lib/mcp-hosts.js`; `rig/lib/host-capabilities.js` is the
source owner and is excluded from the count. A consumer that only checks whether
a host ID exists is not a raw-field reader.

**Chosen check.** Add `scripts/check-raw-registry-access.js`, wired into
`npm test` before the Node test glob. Scan `rig/lib/**/*.js` for a direct import
of `REGISTRY` from `host-capabilities` and subsequent reads of capability fields
such as `mcp_config`, `surfaces`, `instruction`, `native_skill`, or hook fields.
The source owner is exempt. A read outside the allowlist fails; an allowlist
entry whose file or field is no longer present also fails. Print exactly
`raw registry debt: <count>` on every run. The count may decrease in a later
change; any increase is a failure.

This is deliberately lexical and scoped to the current CommonJS import shape.
It is a release ratchet, not a whole-language semantic analyser. If imports are
later refactored to aliases or ESM, replace the scanner with an AST check in the
same script and preserve the no-increase rule.

**Tests to write first.** Create `tests/raw-registry-allowlist.test.js`, using
temporary miniature `rig/lib` trees and a temporary allowlist passed by command
line. The checker accepts `--root <rig root>` and `--inventory <allowlist>` for
these fixtures. Do not unit-test a helper directly.

| Test title | Fixture | Required result |
|---|---|---|
| `the committed raw-registry inventory is the only allowed debt list` | Real repository | Exit zero and prints the committed count; every listed file/field is currently present. |
| `a new raw capability reader fails the ratchet` | Extra module imports `REGISTRY` and reads `mcp_config` | Non-zero exit names the module and field. |
| `an allowlist entry cannot hide missing debt` | Allowlist names a file/field absent from the fixture | Non-zero exit names the stale entry. |
| `the source owner and host-id validation are not counted as consumers` | Source owner plus a module that only tests `REGISTRY[id]` | Zero exit and debt count excludes both. |
| `the ratchet never writes target-runtime artifacts` | Run the normal install fixture | Installed tree has no `HostContract`, raw-registry manifest, resolver, or semantic runtime file. |

**Completion command.** Run `node --test tests/raw-registry-allowlist.test.js`,
then `npm test`. The release's debt count is the number printed by the checker,
not a second prose table. This ticket remains otherwise Backlog for v5.1.

### Scope, again

The migration is a **working order, not a governance artefact**. No phase-gate
ceremony, no numbered regime, no name for the architecture — same reasoning as
the two-fitness-functions limit above.

## The pattern already exists in this repo (added 2026-08-25)

This is not a new principle to adopt. Two facts are **already** handled by
generation here, and their own header comments state the rule:

- `scripts/build-openclaw-skills.js` — *"The body is copied verbatim from
  `skills/<name>/SKILL.md` so the ruleset never drifts."*
- `scripts/build-review-doctrine.js` — *"...so the review skill's copy of the
  ladder can never drift from the one rig actually ships. Same
  generate-then-verify shape as `build-openclaw-skills.js`:
  `tests/review-doctrine.test.js` fails if the committed copy goes stale."*

The mechanism is three parts: one authored source, a `build-*.js` that derives
the copy (a whole file, or a `<!-- BEGIN GENERATED ... -->` block inside a
hand-written file), and a test that fails when the committed derivative is
stale.

**Neither of those two facts has ever produced a review finding.** Every finding
this project has received comes from the ten facts handled by comparison guards
or by nothing. So the work in this ticket is *"apply the pattern we already run
to the rows that do not have it"* — mechanical, finite, and reviewable — not a
philosophical change.

## The ratchet is not optional (added 2026-08-25)

A collapse without a monotonic constraint re-inflates. This project has unified
before: `192f35e` "Unify MCP renderer dispositions" ended with a **third** MCP
table. So the new-twin check in Acceptance is load-bearing, and it must stay
**one check plus a manifest** — [[2026-08-20-first-attempt-retrospective]] lists
over-engineered governance as a past mistake, and a de-duplication programme
that grows its own governance layer has re-created the problem it is fixing.
