## Problem

`wiki/gate1/testing-infrastructure.manifest` byte-pins five files under the
owner's SSHSIG:

```
scripts/check-advanced-spec.js
tests/advanced-oracle.test.js
tests/advanced-spec-gate.test.js
tests/helpers/advanced.js
wiki/gate1/package-scripts.json
```

`tests/advanced-oracle.test.js` is an **enumerated list of 68 acceptance cases**,
63 of which bind through `api(file, name)` — `require(rig/lib/<file>)[<name>]`,
one module, one exported function, called alone.

Pinning an enumeration has three consequences the signature was not intended to
have:

1. **The checked surface is capped at sign time while the code grows.** New
   modules and new hosts arrive with zero signed coverage, by construction.
2. **Every coverage increase costs a ceremony.** Three re-signs in twenty
   commits already. The cost falls on exactly the action the project most needs.
3. **Agents hit a wall and stop.** [[2026-08-24-rig120-review-round2-findings]]
   records it verbatim: *"I cannot edit that test file without invalidating the
   owner's signature."* The freeze meant to protect the definition of acceptable
   is instead blocking it from being met.

A signature should pin **what acceptable means**, not a sample of it. Pin the
properties and the generator, and the owner keeps full authority over the
definition while coverage tracks the code automatically.

## Recommended direction

1. **Split the file.** Properties (what must hold) separate from instances
   (what they hold over).
2. **Derive instances.** The case list comes from `REGISTRY` + the `rig/lib`
   module list, not from 68 literals. Every existing case must still run and
   pass as a generated instance — this is a refactor of the enumeration, not a
   relaxation of it.
3. **Bind at the shipping seam.** Today only 5 of 65 reach it. New properties
   must fail when the *user-visible* behaviour fails, not when a mechanism is
   absent — see the proxy ladder in [[testing-strategy]].
4. **Re-sign once, inside [[RIG-120]]'s ceremony.**
5. **Manifest pins the property file and the generator.** A new host then
   extends coverage without touching a signed byte.

## Acceptance

- The signed manifest pins a property file and a case generator; it no longer
  pins an enumerated case list.
- All 68 current cases run and pass as generated instances (no coverage loss at
  the swap).
- Adding a host row to `REGISTRY` increases the number of executed oracle cases
  with **no** change to any signed file — proven by a test that adds a fixture
  host and asserts the case count rises.
- At least the [[RIG-125]] loop-breaker properties bind at the shipping seam.
- Exactly one re-sign ceremony is consumed, shared with [[RIG-120]].

## The enumeration is partly aimed at code that does not ship (added 2026-08-25)

The strongest single argument for this ticket, found while running the pre-v5
classification ([[2026-08-25-prev5-classification-and-migration-pattern]] §3c):

`tests/advanced-oracle.test.js:351` —
`api('host-capabilities.js', 'materializeSelectedHosts')` — is **one of the 68
byte-pinned cases**, and `materializeSelectedHosts` has **zero production
callers**. Meanwhile `contractFor`, which writes host-contract descriptors into
users' repositories from `rig apply`, carries **no signed case at all** — and is
currently emitting descriptors that contradict shipped owner decisions
([[RIG-134]] 134.1).

So the enumeration is not merely too small. Part of the capped, ceremony-gated
coverage budget is certifying dead code while the shipping path is uncertified.
An enumeration cannot self-correct for this; a property quantified over the
current model would never have been written against a function nothing calls.

## Sequencing (added 2026-08-25, third investigation)

This ticket moves **ahead of [[RIG-125]]**, not alongside it. Order:
[[RIG-131]] → [[RIG-132]] → this → [[RIG-125]] → 126/127/128, with [[RIG-130]]
