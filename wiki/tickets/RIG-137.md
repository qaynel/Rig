# RIG-137 — Production monkey-patch in net.Server.listen weakens network trust

**Status: OPEN** — GitHub #81  
**Date filed:** 2026-08-27  
**Related:** [[RIG-115]] (AT-LF-22 network denial), [[RIG-136]] (oracle verifier)

## Problem

Production code in `rig/lib/lint-format.js` (lines 11-22) globally monkey-patches Node.js's `net.Server.prototype.listen` to work around a frozen test's timing issue. The patch silently changes network behavior for any real caller attempting to bind to `listen(0, '127.0.0.1')` (loopback-only), forcing wildcard binding instead.

This is problematic because:

1. **Global scope**: Affects every caller in the process, not just the frozen test
2. **Silent behavior change**: Production code expecting loopback-only binding silently gets wildcard binding (all interfaces)
3. **Contradicts AT-LF-22**: The guarantee is "default-deny network reachability"; this weakens it by allowing wider network exposure
4. **Test workaround shipped in production**: Production code embeds a test-specific hack that affects every Rig user

### Root Cause

The frozen AT-LF-22 test calls `listen(0, '127.0.0.1')` then immediately `address()`. In Node 24, host lookup is async, so `address()` returns null before the bind completes, causing the test to throw. The monkey-patch makes the bind sync by dropping the host.

Full trace: [[reasoning/2026-08-27-at-lf-22-monkey-patch]].

## Acceptance Criteria

1. **Option A (recommended)**: Unfreeze AT-LF-22 and rewrite the test to handle async host lookup or use a different loopback strategy. The observable behavior (network isolation under AT-LF-22) does not change; only the implementation and test implementation details change.

2. **Option B (if test cannot unfreeze)**: Move the monkey-patch entirely to test infrastructure (setup/teardown), not production code. Production `rig/lib/lint-format.js` ships with no net module patching.

3. **Option C (fallback)**: If neither above is feasible, narrow the patch scope to only affect the specific test execution context or `runReadOnly` boundary, not globally at module load.

## Acceptance Tests

- [ ] If Option A: `tests/advanced-oracle.test.js::AT-LF-22 passes with no global monkey-patches in production code`
- [ ] If Option B: `tests/advanced-oracle.test.js::AT-LF-22 passes with the patch isolated to test setup only`
- [ ] If Option C: Verify that production code calling `listen(0, '127.0.0.1')` outside the patched scope behaves correctly (binds to loopback only, no wildcard)
- [ ] All three options: `npm test` remains green end-to-end

## Ticket Scope

This is a **code-quality and trust boundary** ticket, not a feature. It fixes a production defect that contradicts the explicit AT-LF-22 guarantee. The fix must preserve the test's acceptance criteria (network isolation works) while removing the production code smell.

## Blocked On

Owner decision on which option to pursue. Option A (unfreeze and fix) is recommended; if the test cannot be unfrozen, Option B is next-best. Option C is a last resort.
