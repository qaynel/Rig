## Problem

The product promise is a smooth interactive onboarding
(`inspect → host review → recommend → plan → apply → check`). On the flow a real
user actually follows — `rig/bootstrap.sh --with-runtime`, then the printed
commands — the sequence dead-ends after `inspect`, and the manual MCP step never
appears. Structural root cause is [[RIG-125]]; this ticket tracks the concrete
onboarding gaps to a coherent, runnable flow.

## Sub-findings

- **126.1 (Critical) — printed next-steps are not runnable.**
  `rig/bootstrap.sh:124-134` prints `recommend`/`plan`/`apply` commands whose
  inputs no printed step produces:
  - `review.json` — required by `recommend`/`plan`/`apply` (`validateReview`
    demands a `verdict`, `catalog.js:116-122`) but `inspect` emits no verdict
    (`inspect.js:146-155`). The "host review" stage that would produce it is not
    a subcommand (`cli-advanced.js:16`; `adoptionVerdict` at `inspect.js:157` is
    wired to nothing).
  - `rig.json` — the plan/apply `--manifest` (schema `validateRigJson`,
    `plan.js:21`) is distinct from the `menu.json` `recommend` emits; no printed
    step converts advisory menu → selection manifest.
  - `approval.json` — the content-bound apply `--approval` has no printed
    generator.
  - The inspect line prints a literal `--host <host-id>` that runs verbatim.
- **126.2 (Important) — Antigravity manual MCP step is buried.** The renderer
  (`credentials.js` writeMcpSetup/writeCredentialOutputs) is only called from the
  legacy Basic path (`materialize.js:50`); the staged/`--with-runtime` flow never
  calls it (`apply.js` does no MCP/credential rendering). So `.rig/mcp-setup.md`,
  the README pointer, and the `rig check --host antigravity` prompt never appear
  for the target flow.
- **126.3 (Important) — `rig check --host antigravity` mis-verifies.** With no
  receipt (the staged/runtime case) it falls back to only checking that a
  `rig`-named server exists in the global file (`credentials.js:99-128`), never
  comparing to what onboarding told the user to paste. False pass on a stray
  `rig` entry; false fail when the correctly-pasted server is not named `rig`
  (the setup doc names it from `receipt.manualEntries.antigravity`, which need
  not be `rig`).
- **126.4 (Minor) — final `rig check` is silent on success.** `checks.js`
  reports are failure-only; on a fresh runtime install `runChecks` returns
  `{status:0}` with empty stdout, so onboarding's last step gives no "all good"
  confirmation — a user cannot tell success from a no-op.
- **126.5 (Minor) — `rig/bin/rig` wrapper resolves only post-install**
  (`rig/bin/rig:2` → `../runtime/rig/materialize.js`); running from the source
  checkout fails. Location-coupled; note for docs/error message.

## Why it matters

"Extremely smooth onboarding" is the headline product property. As shipped, a
user who follows the documented flow is blocked immediately after step 1 and, on
an Antigravity repo, is never told the one manual step MCP needs. This is the
onboarding half of production readiness.

## Recommended direction

Add the missing `host-review` stage (inspection → verdict-bearing `review.json`)
and a menu→`rig.json` selection step, or collapse the flow so the printed
commands chain with real defaults; render the manual MCP step and check on the
staged path; make the antigravity check compare against the pasted/expected
server name; print a positive confirmation on a clean `check`. Gate the fix with
the end-to-end "printed sequence runs to green check" test from [[RIG-125]].

## Low-context implementation packet

**Outcome.** A fresh runtime install prints a sequence a stranger can follow
without guessing a filename, host ID, selection schema, or approval digest. The
sequence may pause for a real human approval; it must never manufacture that
approval or silently turn a recommendation into a selection.

**Chosen command contract.** Add two orchestration-only commands while retaining
the existing domain functions:

```text
rig host-review --target <repo> --inspection <inspection.json> --out <review.json>
rig select --menu <menu.json> --service <service-id>=<grade> [--service ...] --out <rig.json>
```

`host-review` reads the inspection, passes its findings through
`adoptionVerdict`, and writes the exact review schema already required by
`recommend`, including the inspection's harness digest and selected host. It
must refuse a stale or malformed inspection. `select` accepts only service IDs
present in the menu and supported grades; it writes the existing `rig.json`
schema and does not execute code or write target configuration beyond that
selection file.

The bootstrap must print these commands in order with `--hosts auto`, never a
literal placeholder. After `plan`, it must explicitly state that the user must
approve the exact plan through the existing host-native or external-signature
path before `apply`. It must not create an `approval.json` with `verified: true`.
If the implementation cannot produce a cryptographically verified plan approval
through an already-existing approval seam, stop and raise that as a separate
trust-boundary task; a test fixture may supply a valid approval receipt, but
production code may not fake one.

**Antigravity boundary.** The staged path must call the existing credential/MCP
output writer with the same selected-server receipt the legacy path uses. If the
staged plan has no selected MCP server, emit no invented server object; write a
short setup document that says no server was selected and keep `check --host
antigravity` actionable. When a manual entry exists, its exact name and object
are the only values `verifyManualMcp` compares.

**Tests to write first.** Create `tests/runtime-onboarding.test.js`. Use the
installed `.rig/bin/rig` entrypoint in a temporary repository, not direct calls
to the library functions. A test approval receipt may use the existing advanced
test helper; that isolates this ticket from the separate cryptographic approval
issuer while preserving apply's content-bound validation.

| Test title | Setup | Required assertion |
|---|---|---|
| `runtime bootstrap prints a runnable staged sequence` | Run bootstrap with runtime into a fresh repo | Output contains `inspect --hosts auto`, `host-review`, `recommend`, `select`, `plan`, `apply`, and `check`; it contains no angle-bracket placeholder or unexplained input file. |
| `the staged sequence produces review selection plan and a green check` | Follow the printed commands with one explicit service selection and a fixture approval receipt | Each command succeeds, each output exists and validates, apply succeeds, and final check prints a positive success message. |
| `host review preserves inspection identity and blocks unsafe findings` | Valid inspection then one with a blocker finding | Valid output carries the original harness digest and `ALLOW`; blocker output is `BLOCK` and downstream recommend refuses it. |
| `selection is explicit and never runs repository code` | Valid menu with a selected and an unselected service | `select` writes only `rig.json`, rejects unknown service/grade, and no service command or target graft is created before apply. |
| `staged antigravity onboarding renders the same manual entry it verifies` | Staged plan/receipt containing a non-`rig` Antigravity manual server name | `.rig/mcp-setup.md` contains that exact object and check prompt; matching global config passes, a stray `rig` entry fails, and a mismatched selected entry fails. |
| `a clean staged check confirms success` | Successful staged apply | Exit zero and stdout contains a stable positive confirmation; a failed check remains non-zero with diagnostic output. |
