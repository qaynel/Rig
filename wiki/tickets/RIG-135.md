## Problem statement

**When this codebase ends a spawned process — by timeout, cancel, parent
signal, or graceful shutdown — cleanup does not recurse.** The kill signal
reaches the direct child only. Every process the child had already forked
(and every process those forks in turn spawned) survives, gets reparented to
init, and keeps running unsupervised. "Ended" today means "the pid we were
watching stopped," not "the work tree rooted at that pid stopped."

The consequence is a class of bugs that all present the same way from the
outside — a process the tool thought it terminated is still alive, holding
a lock, consuming a token/API budget, occupying a slot — and each instance
looks like a new mystery the first time it's investigated.

**The general fix is recursive termination.** Every spawn must be launched
in a container we own (process group on POSIX, job object on Windows), so
that when we tear it down we can signal the whole subtree — direct child,
grandchildren, and further descendants — with a single system call.
Anything less is a partial cleanup.

### F. Bun-native process spawns — needs subsystem-owned design, not a mechanical migration

Sites P7, P16, and P11 (`browser-skill-commands.ts`, `xvfb.ts`,
`cookie-import-browser.ts`) share a real descendant-orphan risk **and** a
reason they cannot simply route through `rig/lib/spawn-guarded.js` as
currently scoped: they spawn through Bun's own `Bun.spawn`/`Bun.spawnSync`
API, not Node's `child_process`, which the helper's declared API
(`spawnGuardedSync`/`spawnGuarded`, Node-`ChildProcess`-shaped) is modeled on.

Verified against Bun's own documentation (not assumed to match Node): Bun
only puts a child in its own process group/session if `detached: true` is
passed (`setsid()`), and Bun's `Subprocess#kill()` does not currently accept
a negative pid — [oven-sh/bun#15791](https://github.com/oven-sh/bun/issues/15791)
tracks this as a `RangeError`. So even a correctly `detached: true` Bun child
cannot be group-killed through the subprocess handle the way
`scripts/review-receipt.js`'s Node-based reference implementation does.

This needs the browse-skill owner to choose one of two paths before these
three sites migrate: (a) route these specific call sites through Node's
`node:child_process` instead of `Bun.spawn` (Bun supports it as a
compatibility shim), so the existing Node-shaped helper applies unchanged, or
(b) design a Bun-native equivalent that calls the OS `kill(2)` syscall
directly on the negative pid rather than through `Subprocess#kill()`. Recorded
here rather than folded into the `debt` list because the fix shape is not yet
decided — an owner decision this ticket does not have standing to make on its
own.

`cookie-import-browser.ts` (P11) additionally needs a Windows Job Object
design for its Chromium launch — this repo has no Windows CI runner today, so
that half of the fix has no automated verification path yet either.

Also found, not part of the classification: the `xvfb.ts` "spawn detached"
comment does not match its code (no `detached: true` is actually passed) —
a separate, smaller defect worth its own fix independent of RIG-135.

## Follow-up — RIG-135.1 (Important, found 2026-08-26, OPEN — GitHub #78)

**A real headless Chromium browser is launched against the user's actual
installed Chrome/Edge profile and killed with a bare leader-pid kill — an
orphan here holds a lock on the user's real browser, not a scratch one.**

`rig/catalog/skills/browse/src/cookie-import-browser.ts`, `importCookiesViaCdp`
(~lines 860-929, Windows-only path): `Bun.spawn([exePath,
--remote-debugging-port=..., --user-data-dir=<the real Chrome/Edge AppData
profile>, --profile-directory=..., --headless=new, ...])`. The code's own
comment says the real profile directory is required because "v20 ABE keys
are path-bound" — this cannot be pointed at a scratch/rig-owned profile
instead without breaking the feature. Cleanup is `chromeProc.kill()` at two
sites (wsUrl-not-found-within-15s, and a `finally` block) — leader pid only,
no Windows Job Object, and Bun's `Subprocess#kill()` does not support a
negative-pid group-kill even if the code tried
([oven-sh/bun#15791](https://github.com/oven-sh/bun/issues/15791)).

This spawn happens inside an HTTP command handler nested in the
already-running browse daemon (`cli.ts`, tracked as this ticket's own site
10, class `debt`). That nesting provides no protection today: the daemon's
own shutdown path (`killServer()`) only ever signals its own leader pid and
never reaches into a nested `chromeProc` a request handler spawned.

**Why it matters:** an orphaned instance keeps the user's real Chrome/Edge
profile locked, which can block the user's actual browser from launching
afterward — materially worse than any other orphan risk found in this
triage pass, because every other site either doesn't fork or touches only
scratch/rig-owned state.

**Open decision, not this ticket's to make alone:** the ticket's own
proposed resolution already names "job-object equivalent on Windows" as a
requirement, but this repository has no Windows CI runner, so a fix here has
no automated verification path today. The browse-skill owner needs to
decide: (a) design and implement a Windows Job Object primitive for this
spawn specifically, accepting it ships without CI coverage and relying on
manual/owner verification, or (b) redesign cookie import to avoid holding a
live Chromium process against the real profile at all (e.g. a
launch-read-close sequence with a hard OS-level watchdog instead of an
open-ended debug-port session). Recommend (a) only if a Windows test
environment is available to the owner; otherwise (b) is likely cheaper to
verify than to build CI for.

**Proposed acceptance (draft — not yet reviewed or signed off):**
- On any exit path (success, timeout, cancellation), the Chromium process
  this file launches is confirmed terminated together with any process it
  forked, not just its leader pid.
- The fix has some form of verification the owner accepts as adequate given
  the no-Windows-CI constraint — real Windows manual verification at
  minimum, ideally a scripted/CI check if a Windows runner becomes
  available.

## Follow-up — RIG-135.2 (Important, found 2026-08-26, OPEN — GitHub #79)

**A caller-authored skill script is spawned through Bun's own process API
with a bare leader-pid kill on timeout — same risk shape as this ticket's
already-`debt` sites, but Bun's spawn API cannot be fixed the same way.**

`rig/catalog/skills/browse/src/browser-skill-commands.ts`, `spawnSkill`
(~lines 266-277): `Bun.spawn(['bun', 'run', scriptPath, '--',
...opts.skillArgs], {cwd, env, stdout, stderr})`, with a `setTimeout` that
calls a bare `proc.kill()` when `opts.timeoutSeconds` elapses. `scriptPath`
is a caller-authored skill script — arbitrary code, not a fixed one-shot
utility — so it can fork its own children, and none of them receive the
kill signal.

**Why it matters:** identical orphan risk to the runtime-command sites this
ticket already classifies as debt (sites 5-9, `bun`/`brain`/`claude` with a
bare timeout), but this call goes through `Bun.spawn` rather than
`node:child_process`. Verified against Bun's own documentation: `Bun.spawn`
only creates a new process group/session (`setsid()`) when `detached: true`
is explicitly passed (not the case here), and Bun's `Subprocess#kill()`
does not accept a negative pid
([oven-sh/bun#15791](https://github.com/oven-sh/bun/issues/15791)) — so
`rig/lib/spawn-guarded.js`'s current Node-`ChildProcess`-shaped design
cannot simply be dropped in here even after implementation lands.

**Open decision, not this ticket's to make alone:** the browse-skill owner
needs to choose the fix shape: (a) route this call through
`node:child_process` instead of `Bun.spawn` — Bun supports it as a
compatibility shim — so the existing (once-built) helper applies unchanged,
or (b) build a Bun-native equivalent that calls the OS `kill(2)` syscall on
the negative pid directly, bypassing `Subprocess#kill()`. (a) is very likely
the cheaper path unless there's a reason this file specifically needs Bun's
own spawn API (e.g. a performance property `node:child_process` doesn't
give it under Bun) — worth confirming with the owner rather than assuming.

**Proposed acceptance (draft — not yet reviewed or signed off):**
- Cancelling or timing out a skill script kills the whole process tree it
  started, not just the `bun run` leader.
- The fix shape decision (shim vs. Bun-native) is recorded before
  implementation, so it isn't re-derived per call site.

## Follow-up — RIG-135.3 (Minor/Moderate, found 2026-08-26, OPEN — GitHub #80)

**The intentional long-lived Xvfb daemon is not actually process-group
isolated despite a comment claiming it is, and its cleanup only signals the
direct pid.**

`rig/catalog/skills/browse/src/xvfb.ts`, `spawnXvfb` (~lines 131-165):
`Bun.spawn(['Xvfb', display, '-screen', '0', '1920x1080x24', '-ac'],
{stdio: ['ignore','ignore','ignore']})`, immediately followed by
`proc.unref()`. An adjacent comment reads "Spawn detached: Xvfb's lifetime
is tied to whether we've explicitly killed it via the handle's close()
method, not to the parent process" — but the code never passes
`detached: true`, and per Bun's own docs only `detached: true` calls
`setsid()`. `proc.unref()` only removes the child from Bun's event-loop
keep-alive; it does not detach the process at the OS level. So contrary to
the comment, Xvfb is not actually session-isolated from the daemon today —
a `SIGHUP` to the daemon's session could take Xvfb down with it.
`cleanupXvfb` (~lines 173-185) then signals only the direct pid
(`safeKill`, `SIGTERM` then `SIGKILL`), the same Bun-API compatibility gap
as RIG-135.2.

**Why it matters, and why it's lower priority than .1/.2:** Xvfb itself
does not typically fork long-lived descendants in normal operation, so the
realistic blast radius of the group-kill gap alone is small. The comment/
code mismatch is the more interesting finding — it means the *intended*
design (daemon-independent Xvfb lifetime) isn't what's actually implemented,
which is exactly this ticket's own Category C: "detached daemons with no
descendant-cleanup contract... individually correct in intent, but there is
no contract that the daemon will itself tear down its own children."

**Open decision, not this ticket's to make alone:** the browse-skill owner
needs to decide Xvfb's actual intended lifetime contract (tied to the
daemon's session, or genuinely independent as the comment claims) and then
make the code match it — either add `detached: true` and fix `cleanupXvfb`
to group-kill (same Bun-native-kill caveat as RIG-135.2), or drop the
misleading comment if session-tied lifetime is actually fine.

**Proposed acceptance (draft — not yet reviewed or signed off):**
- The code's actual detachment behavior matches what its own comment
  claims, one way or the other.
- `cleanupXvfb` terminates the full process tree it started, not just the
  direct pid.

## Localization summary — where the fix must land

Two exact classes of call site to fix, and one gap in the current pattern:

1. **Anywhere `child.kill(sig)` / `process.kill(child.pid, sig)` is called
   on a process that can fork.** Sites 1–4 above. Replace direct-pid kill
   with group-signal via the helper.
2. **Anywhere `spawnSync` / `spawn` sets a `timeout:` option on a runtime
   command (`bun`, `brain`, `claude`, bash scripts, etc.).** Sites 5–9
   above. Replace with the helper's guarded-timeout entrypoint.
3. **Every detached daemon spawn needs a documented descendant-reap
   contract at the daemon side.** Sites 10–13. If the daemon doesn't own
   its subtree, the CLI must — via the helper.

## Why one shared helper, not N narrow fixes

- The pattern has already been independently reinvented **twice** in this
  codebase (site 1 tried; site 14 got it right). Two files, two
  understandings, one wrong. A missing abstraction.
- Precedent: the install/uninstall journal already gives an enforced,
  tested "no half-done work" guarantee for file operations. Processes
  currently have no equivalent. This ticket extends the same rule.
- Narrow fixes force every new spawn site to re-derive the correct answer
  from scratch. A guard step at build time (below) makes the shared path
  the only path new code can take.

## Proposed resolution

Introduce `rig/lib/spawn-guarded.js` (name TBD) with a **recursive
guaranteed-cleanup contract**:

1. Every spawn launches the child in its own container: `detached: true` +
   `stdio` wired appropriately on POSIX; job-object equivalent on Windows.
2. Every terminal outcome (timeout, cancel, parent SIGTERM/SIGINT,
   abnormal exit, normal completion after error) signals the **whole
   subtree** — direct child, grandchildren, deeper descendants — with
   escalating SIGTERM → wait → SIGKILL semantics. Recursion is implicit
   because a POSIX process group / Windows job object contains all
   transitive descendants by default; the helper just has to *use* the
   negative-pid / job-terminate call.
3. Both sync (`spawnSync`-shaped) and async (`ChildProcess`-shaped) entry
   points so existing call sites port over without shape changes.
4. Per-invocation cleanup callback the helper always runs on any terminal
   outcome (temp dirs, checkpoints, lock releases) — folds in the ad-hoc
   staging-dir cleanup currently open-coded in
   `rig-memory-ingest.ts::installSignalForwarder`.
5. Parent-exit safety: registers a global handler once so an abnormal
   parent exit still tears down every guarded child's subtree, not just
   the ones with local `process.on('exit')` handlers. Node's `exit` event
   does not fire on SIGKILL of the parent — the helper documents this
   limit and uses OS-level parent-death signals where available
   (`prctl(PR_SET_PDEATHSIG)` on Linux, job object on Windows) so
   descendants die with the parent.

## Acceptance criteria

  `tests/spawn-guarded.test.js::spawnGuarded cancel kills the entire
  descendant subtree, not just the direct child` — spawns a stand-in that
