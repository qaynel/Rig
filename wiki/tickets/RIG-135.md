# RIG-135 — Guaranteed subprocess cleanup: shared helper, no orphaned descendants

**Status: OPEN (2026-08-26) — Follow-up from [[RIG-124]] 124.1. GitHub #75.**
Ticket: RIG-135 on [[Tickets]].

## Problem

When this codebase spawns a subprocess and later kills it (timeout, cancel,
parent SIGTERM), the kill only reaches the direct child. Anything that child
had already forked survives — reparented to init, invisible to the parent,
consuming budget, holding locks. "Cancelled" does not currently mean
"stopped."

RIG-124.1 fixed one instance narrowly (`scripts/review-receipt.js`). This
ticket is the general version: close the class of bug, not one instance.

## Evidence this is a pattern, not a one-off

Investigation of the current tree turned up **two** independent, ad-hoc
reinventions of subprocess cleanup already in the codebase — same problem,
each solved locally, neither knowing about the other:

1. **`scripts/review-receipt.js` (`RIG-124.1`, just landed).** Uses
   `detached: true` + `process.kill(-run.pid, 'SIGKILL')` on the negative pid
   to signal the whole process group. This is the correct pattern.
2. **`rig/catalog/plumbing/bin/rig-memory-ingest.ts` (`installSignalForwarder`,
   line ~1343; `runbrainImport` timeout, line ~1427).** Installs SIGTERM/SIGINT
   forwarding to a tracked `_activeImportChild`, plus staging-dir cleanup. The
   comments call the exact hazard out by name ("brain orphans, holds the lock,
   next run fails"). **But** the kill is `process.kill(child.pid, "SIGTERM")` —
   the direct pid, **not** the process group. The `brain import` child runs
   `bun` and can fork; anything it forked survives the timeout. This has the
   same latent orphan bug RIG-124.1 just fixed, in a second location, with
   author comments proving the same lesson was already learned once.

Two files, same bug, two different partial cures. That is the signature of a
missing abstraction.

## Why "one shared helper" over N narrow fixes

Precedent exists in this project: file operations go through an
install/uninstall journal specifically so a crash mid-write can't leave
orphaned state on disk. That guarantee is enforced and tested — not just
good intentions. Nothing today gives the equivalent guarantee for
processes. Extending the same "no half-done work" rule to spawns is
consistent with how this codebase already handles the disk equivalent.

Narrow fixes are also demonstrably insufficient: RIG-124.1 proved the
pattern, `rig-memory-ingest.ts` proves the pattern, and any future spawn
site will start from zero again. A shared helper closes the class.

## Proposed resolution

Introduce a single subprocess-spawn helper (`rig/lib/spawn-guarded.js` or
similar) that provides a guaranteed-cleanup contract:

1. Launches every child in its own process group (`detached: true`,
   `stdio` wired appropriately).
2. On timeout, cancel, parent SIGTERM/SIGINT, or abnormal exit, signals the
   **entire group** with escalating SIGTERM → SIGKILL, not just the tracked
   pid.
3. Exposes both sync (`spawnSync`-shaped) and async (`ChildProcess`-shaped)
   entry points so existing call sites port over without shape changes.
4. Cross-platform: on Windows, use the equivalent job-object / tree-kill
   path (the current `spawnbrainAsync` already special-cases Windows
   `shell`; the helper owns that concern once).
5. Callers register per-invocation cleanup (temp dirs, checkpoints) that
   the helper runs on any terminal outcome, so the "kill child + clean
   staging dir" pattern in `rig-memory-ingest.ts` becomes a one-liner.

Migration: `scripts/review-receipt.js` and
`rig/catalog/plumbing/bin/rig-memory-ingest.ts` are the two mandatory
migrations in this ticket (they are the two known-affected sites). The
remaining inventory migrates opportunistically; the acceptance test
prevents new call sites from bypassing the helper.

## Acceptance (draft, owner review pending)

- A shared spawn helper exists with a documented guaranteed-cleanup
  contract (process-group kill, escalating signals, per-invocation cleanup
  callback).
- A regression test: spawn a stand-in that forks a long-lived grandchild
  before the parent is killed; assert no descendant survives the helper's
  cancel path. Test fails against direct `process.kill(child.pid, …)`
  (i.e., would have caught the `rig-memory-ingest.ts` latent bug).
- `scripts/review-receipt.js` and
  `rig/catalog/plumbing/bin/rig-memory-ingest.ts` both route through the
  helper; their existing regression tests remain green.
- A lint/check step (or a named test) fails the build if a
  new `child_process.{spawn,spawnSync,exec,execFile,execFileSync}` import
  appears outside the helper's own file and an explicit allowlist for
  short-lived, cancel-safe utilities (e.g., `git rev-parse`).
- `wiki/index/invariants.md` gains an invariant: "every spawned subprocess
  has guaranteed descendant cleanup on any terminal outcome," linked from
  `wiki/index/traps.md` (the orphan-descendant trap, discovered in
  RIG-124.1).

## Out of scope

- Rewriting every one-shot utility spawn (git plumbing, ssh-keygen version
  checks, etc.) — batch migration is fine; this ticket only mandates the
  two known-affected long-running sites plus the guard against new
  bypasses.
- The narrow RIG-124.1 fix already in `qa-prod-finishing-up-v2` — that
  stays as-is until this helper lands and the migration removes it.
