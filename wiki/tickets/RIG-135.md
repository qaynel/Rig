# RIG-135 — Implement guaranteed process cleanup for spawned subprocesses

**Status: OPEN (2026-08-26) — Identified follow-up from [[RIG-124]]. GitHub #75.
Sub-tickets: 135.1 → GitHub #78, 135.2 → GitHub #79, 135.3 → GitHub #80.**
Ticket: RIG-135 on [[Tickets]].

## Problem

When a subprocess is killed or cancelled (e.g., a review timeout), the tool only terminates the directly-spawned process but not any child processes the subprocess had already forked. This leaves orphaned processes running in the background, unsupervised, consuming resources and budget.

**Root cause:** The current kill mechanism targets only the tracked parent process, not the process group. Any child processes spawned by that parent survive the kill signal, creating "dirty leftovers" that persist until the system reaps them.

**Why this matters:** The reviewer launcher is a full agent that plausibly spawns its own subprocesses while working. When a review gets cancelled for taking too long, the work underneath it may not actually stop — it just keeps running in the background, while the tool has already moved on thinking it's done. This pattern likely exists in other places the tool spawns processes, not just the reviewer.

## Scope

This ticket addresses a **class of bugs**, not a single instance. Rather than narrowly fixing the reviewer launcher, implement a general, shared guaranteed-cleanup helper for process spawning that can be used everywhere this tool launches something — similar to how the install/uninstall system uses a journal to guarantee atomicity on disk operations.

## Proposed resolution

Create a shared process-spawning helper that:
1. Launches the subprocess in its own process group
2. On timeout, cancellation, or abnormal termination, signals the **entire process group**, not just the parent
3. Provides a guaranteed-cleanup contract: a cancelled process is guaranteed to have no running descendants afterward

This helper should be used as the standard path for all subprocess launches in the codebase, closing the class of bugs once rather than instance-by-instance.

## Design note

The existing install/uninstall journal pattern (which guarantees no orphaned file state on crash) demonstrates this project already treats "don't leave things half-done" as a hard rule for file changes. Extending this guarantee to processes is a natural and consistent addition.

## Acceptance (draft, owner review pending)

- A shared process-spawning helper exists and provides guaranteed cleanup of all spawned subprocesses and their descendants.
- When a spawned process is killed, timed out, or signals abnormally, no child processes from that invocation survive afterward.
- A regression test forces a spawned stand-in to fork a child before the parent is killed, and asserts no process from that invocation survives the kill.
- The reviewer launcher (from [[RIG-124]]) uses this shared helper for its subprocess spawn.
- Documentation or comment identifies other existing process-spawn locations and notes they should migrate to this helper in future work.

## Sub-findings from the spawn-site triage (2026-08-26)

Triaging this ticket's pending spawn sites produced three findings that are all
**browse-skill owned** and each carry an owner decision this ticket cannot make
alone. Code locations below were re-verified against this branch's source on
2026-08-26.

- **135.1 (Important — highest of the three, GitHub #78) — cookie-import
  Chromium launch orphans a lock on the user's real browser profile.**
  `rig/catalog/skills/browse/src/cookie-import-browser.ts`,
  `importCookiesViaCdp` (Windows path): headless Chromium is launched against
  the user's **real** Chrome/Edge `--user-data-dir`, which the code's own
  comment says is required because v20 ABE keys are path-bound, so it cannot be
  pointed at a scratch profile. Cleanup is a bare leader-pid `chromeProc.kill()`
  at two sites (lines 908 and 927) — no Windows Job Object, and Bun's
  `Subprocess#kill()` accepts no negative pid. Worse than every other orphan
  risk in this triage because an orphan locks the user's actual browser rather
  than scratch state. The spawn is nested inside the running browse daemon,
  whose own `killServer()` never reaches a request handler's `chromeProc`.
  **Decision open:** build a Windows Job Object primitive with no CI runner to
  verify it, or redesign cookie import away from an open-ended debug-port
  session against the real profile.

- **135.2 (Important, GitHub #79) — browse skill scripts spawn through Bun's
  API, which this ticket's helper design cannot group-kill.**
  `rig/catalog/skills/browse/src/browser-skill-commands.ts`, `spawnSkill`
  (line 247+): a **caller-authored** `script.ts` — arbitrary code that can fork
  — is run via `Bun.spawn(['bun', 'run', scriptPath, ...])` with a bare
  `proc.kill()` on the timeout. Same orphan shape as the `bun`/`brain`/`claude`
  sites already classed `debt` here, but `Bun.spawn` only calls `setsid()` under
  an explicit `detached: true` (not passed) and its `kill()` rejects a negative
  pid, so this ticket's Node-`ChildProcess`-shaped helper cannot be dropped in
  unchanged. **Decision open:** route through `node:child_process` (likely
  cheaper) or build a Bun-native negative-pid `kill(2)`.

- **135.3 (Minor/Moderate — lowest of the three, GitHub #80) — Xvfb daemon
  isn't actually detached despite a comment claiming it is.**
  `rig/catalog/skills/browse/src/xvfb.ts`, `spawnXvfb` (line 131+): the comment
  at line 134 says Xvfb is spawned detached with a lifetime independent of the
  parent, but `detached: true` is never passed — `proc.unref()` (line 139) only
  drops Bun's event-loop keep-alive, not OS session isolation — so a `SIGHUP` to
  the daemon's session can take Xvfb with it. `cleanupXvfb` then signals the
  direct pid only. Xvfb rarely forks long-lived descendants, so the group-kill
  gap alone is small; the comment/code mismatch is the real finding, and it is
  exactly this ticket's Category C (detached daemons with no descendant-cleanup
  contract). **Decision open:** make the code match the intended lifetime
  contract, or drop the misleading comment.
