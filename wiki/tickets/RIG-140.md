# RIG-140 — AT-LF-23 only implements wall-clock timeout; memory ceiling is absent

**Class: CORRECTNESS / SHELL TRUST.**
**Status: COMPLETE (2026-08-28) — GitHub #95.**
Ticket: RIG-140 on [[Tickets]].

## Resolved (2026-08-28)

`rig/lib/memory-guarded-exec.js` (a dedicated watchdog process; `runCommand`
in `lint-format.js` delegates to it whenever `memoryLimitMb` is set) polls
RSS every 15ms and kills-and-reports a distinct `memory_exceeded` status,
independent of the timeout path. As of the same-day PR #83 triage pass, the
watchdog also sums the whole descendant process tree (not just the direct
child) and fails closed with `memory_ceiling_unavailable` if `ps` itself
can't be run, rather than silently enforcing nothing (see
`wiki/status.md`'s 2026-08-28 triage entry). Verified: the named `AT-LF-23`
oracle case and `tests/guarantee-coverage.test.js`'s `AT-PROC-1c`
(memory-ceiling kill, independent of timeout) are both green on current
HEAD. Board entry was left OPEN after the initial implementation landed;
corrected during the later triage pass.

## Problem

The AT-LF-23 acceptance text requires:

> A task exceeding a configured memory ceiling **or** wall-clock timeout is
> killed and reported as its own distinct non-passing state, never a hang or
> silent truncation.

Both conditions are required; each is independently lethal.

**What exists:** `runReadOnly` passes `cmd.timeoutMs` to `spawnTask`, which
passes it to `spawnSync` as `timeout`. A process that runs too long is killed
and the result is reported as `timeout`.

**What does not exist:** there is no memory cap anywhere in the implementation.
`spawnSync`'s `maxBuffer` option limits captured output bytes, not RSS. No
`ulimit -v`, no `--max-old-space-size` injection, no cgroups constraint. A task
can allocate unbounded RAM and either OOM the host or spin the GC indefinitely
with no kill signal and no distinct non-passing result emitted by the runner.

The acceptance case requires the memory ceiling breach to produce its own
distinct `status` (analogous to `timeout`). No code path would ever emit that
state today.

## Location

`rig/lib/lint-format.js` — `runReadOnly`, lines 621 and 606–631. The
`timeoutMs` handling is present; the memory-cap side is entirely absent.

## Acceptance (draft — not yet reviewed or signed off)

- A task that exceeds a configured memory ceiling is killed and the result
  carries a distinct non-passing status (e.g. `memory_limit_exceeded`), never
  `completed` with a zero exit code, and never a silent hang.
- The memory ceiling is OS-enforced (not merely a soft check on reported RSS
  after the fact).
- A new test title covering the memory-ceiling kill path is added to
  `tests/advanced-oracle.test.js` (or equivalent) before any implementation
  lands.
- The wall-clock timeout behaviour is unaffected.

## Note on implementation approach

OS-level memory enforcement is platform-specific:
- Linux: `ulimit -v` (address space), or a cgroup v2 `memory.max` applied to
  the child's process group.
- macOS: Seatbelt has no memory cap primitive; `setrlimit(RLIMIT_AS)` via a
  helper shim or a dedicated wrapper process are the two viable paths.

The approach must be decided and approved before implementation. Do not merge a
purely advisory (non-enforcing) check as satisfying this ticket.
