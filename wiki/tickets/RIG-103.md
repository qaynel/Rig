**Original status: DESIGNED — implementation-ready (contained code change + test).**

## Problem
`host-coverage-spec §3.2` lists `pi` as `mcp: 'unsupported'` — "no path may emit
MCP configuration for it," and flags `.omp/mcp.json` as speculative. Yet
`rig/lib/renderers.js` marks `pi` Tier `A`, defines `renderPi`, sets
`HOST_FILES.pi = '.omp/mcp.json'`, and actively writes `mcpServers` for pi
(exercised by `tests/basic-renderers.test.js`). Rig emits MCP config for a host
the governing design says cannot consume it.

## Findings
- `renderers.js:14` puts `pi` in Tier A; `:42` maps its file; `:127 renderPi`
  writes `mcpServers`; `RENDERERS.pi` (`:194`) dispatches it. `renderMcp` will
  therefore emit `.omp/mcp.json` whenever pi is a selected host.
- The spec's required behavior: emit nothing for pi; **preserve** any
  pre-existing user-owned `.omp/mcp.json` and attach *migration guidance* rather
  than deleting it silently. AT-HOST-5 is the case this violates and needs
  explicit coverage.
- `renderers.js` is **not** in the signed oracle manifest → editable without a
  re-sign. `tests/basic-renderers.test.js` asserts current renderPi output and
  must be updated in the same change.

## Solution (contained)
1. Reclassify pi in `renderers.js`: remove `pi` from the Tier-A MCP emitters
   (drop `renderPi`, `HOST_FILES.pi`, `RENDERERS.pi`) and treat pi like the
   advisory/`unsupported` class — `renderMcp` records it in `noteHosts` (advisory
   note) and emits no file. If a pre-existing `.omp/mcp.json` exists, leave it
   byte-for-byte and add a migration note to the receipt.
2. Add a shared `MCP_DISPOSITION` map (`repo` / `user_global` / `unsupported`)
   sourced from §3.2, and assert in a test that every host's renderer behavior
   matches its disposition (this is the seed of the [[RIG-104]] single source of
   truth).
3. Update `tests/basic-renderers.test.js` and add **AT-HOST-5**: selecting pi
   emits no `.omp/mcp.json`, and a pre-existing user file is preserved with
   guidance.

## Alternative (if evidence flips)
If authoritative evidence later confirms pi MCP support, record it in
`host-coverage-spec` and correct the disposition to `repo` instead — the same
`MCP_DISPOSITION` map then keeps renderer and spec in lockstep.

## Sequencing
Natural first slice of [[RIG-104]] (unify the two MCP paths under one
disposition map). Do them together to avoid touching `renderers.js` twice.
