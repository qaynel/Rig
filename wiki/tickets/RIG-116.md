# RIG-116 — Promote the non-lint-format leaves Policy → Context → Evidence

**Status: DESIGNED — phased plan; each promotion is an ordinary gated change.**
Ticket: RIG-116 on [[Tickets]].

## Problem
Delivery-plan step 8: lint-format is the only leaf built past Policy grade; the
other 114 are Policy-only with Context/Evidence promotion deferred post-beta. A
"full-fledged" catalogue delivers higher-grade assurance across families, not one
vertical.

## Findings
D24 keeps the beta boundary at all 115 Policy leaves (status.md); promotion is
explicitly post-beta and returns to "the ordinary owner-reviewed process"
(authored-service-gate topic). So this is a **sequenced program**, not a single
change, and it is correctly *not* a beta blocker.

## Solution (prioritized, family-batched)
1. **Prioritize by evidence of use.** Promote on demand signal, not
   alphabetically: instrument which leaves users actually select (from install
   receipts / onboarding telemetry the beta gathers) and rank families by that.
2. **Batch by family** so shared Context/Evidence check archetypes
   (`AT-SHAPE-1..4`, reused from lint-format) amortize across a family in one
   pass rather than 114 one-offs.
3. **Each promotion = one ordinary gated change.** For a family batch: author
   Context (repository-context checks) then Evidence (real verifiable
   receipt/boundary checks) per leaf, add acceptance, pass the authored-service
   gate, land under the normal gate. No mega-freeze.
4. **Highest-demand families first** reach Context/Evidence with real checks
   (acceptance bullet 2) — likely the Development and Testing families given the
   lint-format precedent.

## Dependencies / gating
Depends on the discovery engine ([[RIG-114]]) for real per-component checks and on
lint-format acceptance ([[RIG-115]]) as the reusable template. Post-beta by D24;
start after the release ([[RIG-120]]). No single owner re-sign — each family
batch re-signs only its own new acceptance.
