# RIG-136 — Oracle success log hardcodes the case count; print the verified count

**Class: MAINTENANCE (cosmetic / honesty of the verifier's own output).**
**Status: OPEN (2026-08-27) — GitHub #92 — found during the wiki/code
sync that closed [[RIG-115]]; out of scope for that wiki-only pass.**
Ticket: RIG-136 on [[Tickets]]. Provenance:
[[2026-08-27-wiki-code-sync-at-lf-24]]. Related: [[RIG-137]].

## Problem

`scripts/check-advanced-spec.js` enforces the live acceptance-ID set in
`verifyCoverage` (`assert.equal(accepted.length, 73, …)` as of 2026-08-27)
and then prints a **separate hardcoded string** on success:

```
Oracle verified: ${entries.length} files, 68 acceptance cases
```

The file count is interpolated. The case count is a leftover literal from
the 68-ID freeze (D24). D28 grew the set to 73 and the assert was updated;
the success line was not. The gate is green and the signature verifies —
the log is simply wrong. Anyone reading `npm test` output is told the
oracle is still 68 cases.

This is the same class as the wiki drift the 2026-08-27 sync corrected:
a second copy of a count, updated in one place and not the other.

## Why it is not a one-line drive-by

`scripts/check-advanced-spec.js` is byte-pinned in
`wiki/gate1/testing-infrastructure.manifest`. Changing the log invalidates
the owner signature. The fix is small; the cost is a re-sign, not the
edit. Do not land it outside a signing window, and do not burn a dedicated
ceremony for a log line.

Not a v5.0.0 blocker. The freeze itself is correct; only the printed
summary lies.

## What "dynamic" means here

Print the count `verifyCoverage` just confirmed. Do **not** drop the
exact-count freeze (`accepted.length === 73` today) — that literal is the
ratchet that forces a ceremony when the ID set grows. The log must be
derived from the verified set so it cannot drift from the freeze again.

`verifyCoverage` already has `accepted`. Return that length (or the
array) from `check()`'s call and interpolate it:

```
Oracle verified: ${entries.length} files, ${acceptedCount} acceptance cases
```

A named constant shared by the assert and the log (`const N = 73`) still
needs a human to bump it on every freeze change — that is how this bug
was born. Derived from `accepted.length` after the assert has passed.

## If [[RIG-133]] lands first

RIG-133 rewrites what the signature pins (properties + generator instead
of an enumerated sample list) and will touch this same signed file. If
that rewrite lands first and the success line is already derived from the
verified set, close this ticket as absorbed. Otherwise this is the
smallest patch that can ride the next re-sign.

## Proposed acceptance (draft — not yet reviewed or signed off)

- After a successful oracle check, the printed case count equals the
  number of acceptance IDs `verifyCoverage` just confirmed. There is no
  numeric literal for that count in the success line.
- The exact-count freeze remains; growing or shrinking the ID set still
  fails until the freeze number is deliberately updated under a re-sign.
- A regression in the signed gate tests fails if the printed count and
  the verified ID set disagree.
  → `tests/advanced-spec-gate.test.js` (new title at implementation time)
- Lands inside an already-needed owner re-sign, not a dedicated ceremony.

## Out of scope

- Changing the freeze number itself, the ID set, or the signed acceptance
  document.
- [[RIG-133]]'s structural change to what the signature pins.
- Wiki prose that still says "68" as dated history (closed tickets,
  timeline, reasoning traces) — those stay.
