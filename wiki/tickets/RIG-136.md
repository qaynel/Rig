## Problem

`scripts/check-advanced-spec.js` enforces the live acceptance-ID set in
`verifyCoverage` (`assert.equal(accepted.length, 73, …)` as of 2026-08-27)
and then prints a **separate hardcoded string** on success:

```
Oracle verified: ${entries.length} files, 68 acceptance cases
```

The file count is interpolated. The case count is a leftover literal from
the 68-ID freeze (D24). D28 grew the set to 73 and the assert was updated;
the success line was not. The gate is green and the signature verifies —
the log is simply wrong. Anyone reading `npm test` output is told the
oracle is still 68 cases.

This is the same class as the wiki drift the 2026-08-27 sync corrected:
a second copy of a count, updated in one place and not the other.

## Why it is not a one-line drive-by

`scripts/check-advanced-spec.js` is byte-pinned in
`wiki/gate1/testing-infrastructure.manifest`. Changing the log invalidates
the owner signature. The fix is small; the cost is a re-sign, not the
edit. Do not land it outside a signing window, and do not burn a dedicated
ceremony for a log line.

Not a v5.0.0 blocker. The freeze itself is correct; only the printed
summary lies.

## What "dynamic" means here — do not hardcode it again

**Rejected as the fix:** changing `"68"` to `"73"`. That is the same bug
with a newer number. Also rejected: `const N = 73` (or any other named
literal) shared by the freeze assert and the log. Both still need a human
to bump a second copy when the set grows — that is how this bug was born.

**Required:** the success line interpolates the **number of tests
present** — the live count of acceptance-case tests the checker just
found in the manifested test files (`testTitleIds` / `titled.length` in
`verifyCoverage`). Same pattern as the file count already next to it
(`${entries.length} files`). After coverage checks pass, that equals the
acceptance-ID set; print the derived length, never a numeral.

```
Oracle verified: ${entries.length} files, ${titled.length} acceptance cases
```

If a later ceremony adds or removes cases, this line follows
automatically. No second edit. No second literal.

The exact-count freeze (`accepted.length === 73` today) is a separate
ratchet and is **out of scope** for this ticket. Do not move that number
into the log; do not delete it either.

## Proposed acceptance (draft — not yet reviewed or signed off)

- After a successful oracle check, the printed case count equals the
  number of acceptance-case tests present in the manifested test files
  (the same set `verifyCoverage` already collects). The success line
  contains **no numeric literal** for that count — not 68, not 73, not a
  `const`.
- A fixture with a different present-test count prints that different
  number. Replacing 68 with 73 (or any other fixed numeral) fails this
  criterion.
- The exact-count freeze in `verifyCoverage` is unchanged.
- A regression in the signed gate tests fails if the printed count and
  the tests-present count disagree.
  → `tests/advanced-spec-gate.test.js` (new title at implementation time)
- Lands inside an already-needed owner re-sign, not a dedicated ceremony.

## Out of scope

- Changing the freeze number itself, the ID set, or the signed acceptance
  document.
- [[RIG-133]]'s structural change to what the signature pins.
- Wiki prose that still says "68" as dated history (closed tickets,
  timeline, reasoning traces) — those stay.
