## Resolution (owner, 2026-08-26)
The owner approved five concrete guarantees closing the shell-trust suite —
single-use plan-bound approval, filesystem/env isolation including through
symlinks, default-deny network reachability, killed-and-reported resource/time
caps, refused symlink escapes (`GA-37`, `D28`). `AT-LF-20`–`AT-LF-24` are
authored in `wiki/gate1/acceptance.md` with matching tests in
`tests/advanced-oracle.test.js` and trace rows in
`wiki/gate2/technical-spec.md` §9.4; the acceptance ID set is **73**. See
[[2026-08-26-rig115-shell-trust-guarantees]].

`AT-LF-20` (single-use plan-bound approval) is implemented in
`rig/lib/lint-format.js` `executePlan`: a matching approval is consumed on
the executed path and the same object is refused as `not_authorized` on
replay. `AT-LF-21` is implemented at task spawn (escaping cwd refused; child
env is an explicit allowlist). `AT-LF-23` is implemented: a configured
`timeoutMs` kills the read-only task and reports `timeout`. `AT-LF-22` and
`AT-LF-24` remain unimplemented and fail by design. Applicability
(`AT-LF-19`) and execution consent (`AT-LF-5`, `AT-LF-12`) were already
covered by the existing signed set and needed no new cases.

## Problem
The lint-format-roadmap marks three contracts "intent frozen, acceptance not yet
authored": partial-install applicability, execution consent (selection
authorizes nothing to run; plan approval authorizes only listed read-only
commands; fixes need separate approval), and shell trust (repo tasks stay
untrusted under policy/privilege/secret/network/resource limits even with
`shell: false`).

## Findings
Intent is frozen (roadmap "Applicability / Execution consent / Shell trust" rows);
what's missing is deterministic `AT-LF-*` acceptance cases. `.rig/bin/check.js`
already runs argv-only with `shell:false` and never dispatches the recorded
`fix` command — so the implementation substrate exists; the tests assert the
contract.

## Solution (three acceptance suites)
1. **Applicability**: given a repo where only some components are covered, Rig
   installs the covered ones and **explicitly reports the uncovered as
   unprotected**; a whole-repository support claim is suppressed. Cases: full
   cover → claim allowed; partial → claim suppressed + named exclusions.
2. **Execution consent** (three-step ladder):
   - Selecting a service runs **nothing** (assert no command executes on select).
   - Approving a concrete plan authorizes **only** its listed read-only commands
     and scopes.
   - A mutating fix requires a **separate** approval; a fix attempted under a
     read-only approval **fails visibly** (acceptance's "leaf task attempts a
     mutation under a read-only approval … fails").
3. **Shell trust**: a repository task is untrusted code under policy, privilege,
   secret, network, and resource/time controls even with `shell:false`; a task
   that escapes the argv boundary **fails visibly**. Cases: argv-escape attempt →
   denied; network/secret access under a leaf task → denied by
   `.rig/network-policy.json`; resource/time cap enforced.

## Blocker reconciliation (2026-08-24)
The current signed 68-case oracle already contains broad cases for selection
consent, approved-plan digests, explicit partial coverage, mutation detection,
separate autofix approval, and the outer argv boundary. That does not resolve
this ticket's requested deterministic shell-trust suite. The existing profile
explicitly labels approval persistence, filesystem/environment isolation,
memory limits, and symlink handling as assumptions; it also requests network
denial that the current process runner does not enforce.

Those guarantees cannot be selected or added to the signed oracle by an
implementing agent. The intent owner must approve or amend the concrete
session-lifetime, filesystem/env, network, resource-cap, and symlink outcomes,
then re-sign the acceptance and runnable tests. Until then, claiming that
`shell:false` supplies those controls would be false. No frozen artifact or
runtime code was changed for this ticket.
